# Working rules (always apply)

## Git
- Never run git commit, git add, git stash, git checkout, or git reset.
- Edit files, then stop and report: files changed + `git status` + `git diff --stat`.
- The developer reviews and commits manually.

## Database
- Schema changes always go in `database/migrations/<date>_<desc>.sql` with UP and DOWN sections
  (e.g. `2026-08-29_add_xyz_column.sql`; more than one file the same day → append `_2`/`_3`).
  One file = one change/feature, never append multiple unrelated changes into one file.
- Never run ad-hoc DDL (CREATE/ALTER/DROP) against any database without a migration file
  backing it first — the file always comes before the DDL runs, never after or instead of it.
- You may apply migrations to the local dev DB only. Never to any other database.
- Report in the task summary that a migration was applied and how to roll it back.
- Report which tasks require a migration to be run before the code works.
- Code that depends on a new column must fail safely or clearly if the
  migration has not been applied.

## Process
- Ask before guessing any business rule.
- Fix logic only unless explicitly told to change UI/style.
- One task at a time; stop and report after each.
- Code comments explain why in one line max. Longer rationale goes in the commit message.
- When asked for a summary or release note, derive it from git log, never from memory.
- Follow the given task order. Ask before reordering.
- Mirror-by-copy is not acceptable: if a new function duplicates an existing one except for a
  parameter, generalize the existing function instead.
- End every task report with a suggested commit message in conventional-commit format
  (type(scope): summary + 1-3 lines of why). The developer copies it when committing.

## Code Convention
- ทุก query ต้องใช้ PDO prepared statement เท่านั้น ห้าม concatenate ค่าที่มาจาก user input ลงใน SQL ตรงๆ
- Controller/Model ใหม่ทุกไฟล์ต้องมี `declare(strict_types=1);`
- ชื่อฟังก์ชันกลางสำหรับ query: `select_data` / `insert_data` / `update_data` (implementation ใช้ PDO ภายใน) — **ยังไม่ได้ implement จริงในโค้ดปัจจุบัน** โมเดลที่มีอยู่เรียก `$this->db->prepare()/execute()` ตรงๆ ในแต่ละ method หากจะสร้าง helper กลางนี้ ให้ทำเป็นงานแยกและ migrate ของเดิมทีหลัง อย่าผสมสองรูปแบบในไฟล์เดียวกัน
- Soft delete pattern: ตารางที่มีการลบใช้ `status enum('active','inactive','deleted')` + `deleted_at`/`deleted_by` ไม่ hard delete ข้อมูล payroll/master data
- Unique constraint ที่มี `deleted_at` ร่วมด้วยต้องเช็คซ้ำระดับ application เสมอ (MySQL ถือว่า NULL แต่ละแถวไม่ซ้ำกัน composite unique key จึงกันแถว active ซ้ำไม่ได้จริง)
- ตารางที่ scope ด้วยบริษัทต้องมี FK `comp_id → companies.id` (`ON DELETE RESTRICT ON UPDATE CASCADE`)
- Testing: โปรเจกต์ยังไม่มี PHPUnit — ใช้ lightweight script ใน `tests/*.php` แทน (รันตรงด้วย `php tests/xxx.php`, print PASS/FAIL, exit code ไม่ใช่ 0 ถ้ามี fail) สำหรับ service class ที่ต้อง unit-testable (เช่น `StatutoryCalculationEngine`, export ใน `app/services/export/`) — ให้ constructor รับ `?PDO $pdo = null` เพื่อ inject ได้ และถ้า test เขียนลง DB จริงให้ครอบด้วย transaction แล้ว rollback เสมอ ไม่ทิ้งข้อมูลไว้ (ดูตัวอย่าง `tests/statutory_engine_test.php`)
- **Model method ที่ทำ multi-step write ต้องเช็ค `$this->db->inTransaction()` ก่อน `beginTransaction()` เสมอ** (pattern: `$own = !$this->db->inTransaction(); if ($own) beginTransaction(); ... if ($own) commit()/rollBack();`) ไม่งั้นถ้าถูกเรียกจากภายใน transaction อื่น (เช่น test script ที่ครอบทั้งไฟล์ด้วย transaction, หรือในอนาคตถ้ามี endpoint ที่เรียกหลาย model ต่อกันในทรานแซคชันเดียว) จะได้ PDOException "There is already an active transaction" แล้ว catch block จะ rollback transaction ของผู้เรียกโดยไม่ตั้งใจ ทำให้โค้ดหลังจากนั้นรันแบบ auto-commit จริงและหลุดออกนอก transaction ที่ตั้งใจไว้ (เจอบั๊กนี้จริงกับ `PayrollRunModel::recalculate/delete/markPaid` ตอนเขียน test — แก้ตามนี้แล้วทั้ง 3 method, และเจอซ้ำอีกรอบใน `EmployeeEarningDeductionModel::save()` ตอนเขียน test fixture ให้ `StudentLoanReport` — แก้ตามนี้แล้ว — เจอซ้ำอีกรอบใน `TaxStatutoryModel::rateHistorySave()` ตอนตรวจสอบ Payslip Format module (สืบไปเจอ TH_SSO/TH_PVD rate history ถูก soft-delete ในทางที่ไม่มีแถวใหม่มาแทน ทำให้ payroll calculation พังจริงใน dev DB — ไม่ยืนยันได้ 100% ว่าบั๊กนี้เป็นสาเหตุของ incident นั้นเป๊ะๆ เพราะ `rateHistoryDelete()` เองไม่ได้เปิด transaction แต่ `rateHistorySave()` มี bug pattern เดียวกันจริง — restore ข้อมูล 2 แถวนั้นแล้ว และ **แก้ `TaxStatutoryModel::rateHistorySave()` ตามนี้แล้ว** (2026-07-23))
- รายการตัวเลือกแบบ fixed/closed set ที่ "อาจมีเพิ่มทีหลังโดยไม่อยากแก้โค้ด" (เช่น ประเภทเหตุการณ์ที่ผูกกับรายการ payroll, รูปแบบไฟล์ธนาคาร) ให้ทำเป็น master table (`id`, `code`, `name_th`, `name_en`, `is_active`, ...) แล้วดึงผ่าน Select2 โหมด `ajax` แทนการ hardcode enum/array ในโค้ด — เพิ่มตัวเลือกใหม่ทีหลังแค่ insert แถวใหม่ ไม่ต้อง deploy โค้ด ตัวอย่าง: `master_payroll_source_events` (ผูก dropdown "Linked Attendance Event" ในหน้า Payroll Configuration, มีคอลัมน์ `applies_to` กรองว่าใช้ได้กับ earning/deduction/both), `master_bank_file_formats` (ผูก `payroll_cycles.bank_file_format_id`, ย้ายมาจาก hardcoded array ใน `PayrollCycleModel` ตอนทำ Reports module — ถ้าเจอ pattern แบบนี้ที่ยังเป็น PHP const array อยู่ที่อื่น ให้ถือเป็น candidate ย้ายเป็น master table เช่นกัน)
- **`StatutoryCalculationEngine::calculate()`/`calculateItem()` รับ `$employeeFlags` (param ตัวที่ 4, optional)** สำหรับเช็คสิทธิ์เข้าร่วมต่อรายบุคคล (เช่น `employees.sso_enrolled`/`pvd_enrolled`/`tax_exempt`) แยกจาก company-wide toggle ใน `company_statutory_settings` — ถ้าไม่ส่ง param นี้มาเลย (default `[]`) engine จะถือว่า enrolled ทุก item (backward compatible) แต่ **`PayrollRunModel::recalculate()` ส่ง flag จริงจาก DB เสมอ** ห้ามลบทิ้งเวลาแก้โค้ดคำนวณ payroll ไม่งั้นพนักงานที่ opt-out ประกันสังคม/ไม่ได้เข้ากองทุนสำรองเลี้ยงชีพ จะโดนหักเงินผิดอีกครั้ง (เป็น bug จริงที่แก้ไปตอนทำ Reports module — root cause คือ engine เดิมคำนวณ statutory item เดียวกันทุกคนในบริษัทแบบไม่แยกรายคน)
- **`PayrollRunModel::recalculate()` เลือกพนักงานเข้า run ด้วยช่วงวันที่ (`employment_date`/`employment_end_date`) เท่านั้น ไม่เช็ค `employees.employee_status`** เพราะพนักงานที่เพิ่งลาออกมักถูกเปลี่ยน status เป็น `resigned` ทันที แต่ยังต้องปรากฏใน run ของงวดสุดท้ายที่ยังจ่ายเงินให้ (pro-rate ถึงวันที่ `employment_end_date`) — ถ้าเพิ่ม filter ด้วย status จะทำให้พนักงานที่เพิ่งลาออกหายไปจาก run สุดท้ายของตัวเองผิดพลาด

(!empty($data['key']) ? 1 : 0) : $currentValue` เสมอ

## UI Convention
- Design: glassmorphism, สีหลัก orange `#FF9900` + gold accent, รองรับ 2 ภาษา TH/EN แบบ dynamic (เปลี่ยนได้โดยไม่ reload หน้า ผ่าน language switcher มุมขวาบน)
- Alert/Confirm ทั้งหมดใช้ **SweetAlert2** เท่านั้น (`showSuccess`/`showWarning`/`showError`/`showConfirm` ใน `public/js/alert.js`) ห้ามใช้ Bootstrap modal หรือ native `alert()`/`confirm()` สำหรับแจ้งเตือน
- ปุ่มหลัก (Add/Save) ต้องเป็นสี brand orange `#FF9900` ไม่ใช่สี Bootstrap default

### Dropdown / Select
- ทุก dropdown ในระบบต้องใช้ **Select2** ห้ามใช้ `<select>` เปล่าไม่ init — ปล่อยเป็น plain select ครั้งเดียวก็แปลภาษาไม่ได้ (option โชว์เป็น i18n key ดิบๆ ทันทีที่ key ไม่ตรง เจอเคสจริงมาแล้วในหน้า Payroll Cycle)
- Initialize ผ่านฟังก์ชันกลาง `initSelect2(selector, options)` ใน `public/js/input.js` รองรับ 3 โหมด อย่าเขียน select2 init ซ้ำใหม่ในแต่ละหน้า:
  - `{ mode: 'ajax' }` (หรือใช้ alias `initSelect2Remote(selector)`) — โหลดจาก DB ผ่าน endpoint ที่คืนค่า `{status, data: {items:[{id, text_th, text_en}], total_count}}`
  - `{ mode: 'static' }` — ตัวเลือก hardcode ไม่ผ่าน AJAX อ่านจาก `data-option-keys="key1,key2,..."` บน `<select>` แล้ว map แต่ละ key ผ่าน `getLangValue(key)`; **ต้องเช็คว่าทุก key ที่ใส่มีอยู่จริงใน `public/lang/en.json`/`th.json` ทั้งคู่ก่อนใช้งาน** ไม่งั้น fallback เป็นการโชว์ key ดิบแทนข้อความแปล
    - **ค่าที่ submit ไปหลังบ้านคือ key ตรงๆ ไม่ใช่แค่ตัวช่วยหา text** — ถ้า backend ต้องการ enum ที่ไม่ตรงกับ i18n key ที่ใช้แสดงผล (เช่น key `calc_fixed_amount` ไว้กันชนกับ key อื่น แต่ backend ต้องการแค่ `fixed_amount`) **ต้องใส่ `data-option-values="value1,value2,..."` เรียงตำแหน่งให้ตรงกับ `data-option-keys` เสมอ** ไม่งั้น select2 จะ submit ค่า key ดิบไปแทน validation หลังบ้านจะ reject ทันที (เจอบั๊กจริงมาแล้ว — บันทึกไม่ลงทั้งหน้า Payroll Configuration เพราะพลาดจุดนี้)
  - `{ mode: 'native' }` — คง native look ไม่มี dropdown UI ของ Select2 แต่ยัง init ผ่านฟังก์ชันนี้เพื่อให้ผ่านกฎ "ห้ามปล่อย select ไม่ init"
- เปลี่ยนภาษาแบบ dynamic: option label ต้องเปลี่ยนตาม language switcher ทันทีโดยไม่ reload หน้า — `applyLanguage()` ใน `public/js/app.js` จัดการ re-init ให้อัตโนมัติทั้ง `.select2-remote.select2-hidden-accessible` และ `.select2-static.select2-hidden-accessible` อยู่แล้ว ไม่ต้องเขียนเพิ่มเอง แค่ใส่ class ให้ถูก
- Placeholder, "no results found", "searching..." ต้อง localize ผ่าน `langData` เสมอ (key: `select_option`, `no_results`, `searching`, `input_too_short`) ห้าม hardcode ข้อความอังกฤษ
- ต้องรองรับ dropdown ที่อยู่ใน Bootstrap modal และ nested tab — ตั้ง `dropdownParent` ให้ชี้ modal ที่ครอบอยู่เสมอ (`initSelect2` เช็ค `$this.closest('.modal')` ให้อัตโนมัติแล้ว) ป้องกันปัญหา z-index/scroll ที่ Select2 เจอบ่อยเวลาอยู่ใน modal
- ตัวอย่างการใช้งานจริงในโปรเจกต์: dropdown ประเทศใน Company Profile/Payroll Configuration (`ajax`), dropdown ธนาคารใน Bank Accounts (`data-api="/api/bank.get" data-type="bank"`, `ajax`), dropdown Calculation Method/Tax Treatment ใน Payroll Configuration (`static`)

### Date Picker (`.datepicker`, `initDatepicker()` ใน `public/js/input.js`, ใช้ bootstrap-datepicker)

- Save/Delete สำเร็จให้ reload ด้วย `table.ajax.reload(null, false)` (พารามิเตอร์ตัวที่สอง `false` = ไม่รีเซ็ต pagination ที่ผู้ใช้อยู่) ห้าม reload ทั้งหน้า

## Business Model — 3 ประเภทผู้ใช้
1. **Origami HR user** — sync attendance/leave/holiday/OT/ค่าเที่ยว อัตโนมัติจากโมดูล HR
2. **External HR user** — Import ผ่าน Excel/CSV template + validation + field mapping
3. **No HR user** — manual entry เต็มรูปแบบ

ทุก entity ที่เกี่ยวกับ attendance/leave/OT ต้องมี field `data_source` (`sync` / `import` / `manual`) เพื่อบอกที่มาของข้อมูล

## Authentication (Origami SSO, `auth/index.php` + `auth/switch.php`)
- **Login เป็น one-way SSO handshake เท่านั้น** — Origami redirect มาที่ `BASE_URL/auth/?token=...`, `auth/index.php` เอา token ไป sign เป็น JWT ยิงไปที่ Origami's `/api/oauth/v2/auth`, ได้ identity กลับมาแล้ว map เข้ากับ `companies`/`employees` ของแอปนี้เอง (auto-provision แถวใหม่ถ้ายังไม่เคย sync มาก่อน ดู comment ยาวในไฟล์นั้นเอง) แล้วตั้ง `$_SESSION['user']` — เป็น session ของ Payroll เองล้วนๆ **ไม่มี token/expiry เชื่อมกับ Origami อีกเลยหลังจากขั้นตอนนี้** `ensure_login()` (`app/helpers/helpers.php`) เช็คแค่ว่า `$_SESSION['user']` มี `employee_id`/`company_id` ในเซสชันของตัวเองหรือไม่ ไม่เคยเช็คย้อนกลับไปที่ Origami เลยว่า session ฝั่งนั้นยังใช้ได้อยู่ไหม

    - Controller (`PayrollController::revert()`) อ่าน `to_state` จาก JSON body แล้วส่งต่อ ฝั่ง UI (`public/js/payroll/approval.js`) เปลี่ยนจากปุ่ม "Undo Decision" ปุ่มเดียวเป็นปุ่ม revert แยกตาม state ปลายทางที่เลือกได้จริง (แสดงเฉพาะปลายทางที่ไม่ใช่ state ปัจจุบันของ request นั้น) แต่ละปุ่มมี modal ยืนยันของตัวเอง (`confirm_revert_to_title`/`confirm_revert_to_message` + label เฉพาะปลายทาง `action_revert_to_pending`/`action_revert_to_rejected`/`action_revert_to_need_info`)
    - ทดสอบด้วย `tests/payroll_run_test.php`'s revert-to-chosen-status section (~18 assertions ใหม่, รวมทั้งไฟล์ 454 assertions) ครอบคลุม: reject ปลายทางเดียวกับปัจจุบันถูกปฏิเสธ, ปลายทางไม่ถูกต้องถูกปฏิเสธ, approved→rejected ตรง (custom note กลายเป็น reject_reason), rejected→need_info ตรง (ใช้ default reason), need_info→pending_approval

## Setup & Rules (`Time & Leave` menu → 5 แท็บ: Shift/Holiday/Leave Type/OT Rate/Work Location)
- Backend เต็มรูปแบบใน `SetupRulesModel`/`SetupRulesController` ครบทั้ง 5 แท็บ
- **OT Rate** (`ot_rates` + `master_ot_scope_types`): "Applies To" (เดิม hardcode Weekday/Weekend/Holiday ใน mockup) ย้ายเป็น master table ตาม convention เดียวกับ leave category/payslip field — seed ไว้ 3 ค่า `calculation_base` ยังเป็น enum('hourly','daily') ธรรมดา ไม่ทำ master table เพราะเป็นตัวเลือกที่ผูกกับสูตรคำนวณจริง ไม่ใช่ list ที่ธุรกิจจะเพิ่มเองได้ตามใจ — **ไม่ผูก scope กับ employee/shift แบบ Holiday** (ไม่มี requirement เพิ่มเติมแบบ Holiday/Leave Type ตอนสั่งงาน จึงทำแค่ระดับ company-wide config ธรรมดา) **ยังไม่ได้ enforce ขั้นต่ำตามกฎหมายแรงงาน** (เช่น 1.5x ขั้นต่ำวันธรรมดา) เพราะไม่มั่นใจตัวเลขที่ verify แล้ว เป็นแค่ config tool ให้ตั้งเอง ไม่ใช่ compliance validator — ทดสอบด้วย `tests/ot_rate_test.php` (13 assertions)
- **`shifts` และ `master_work_locations` ถูกสร้างขึ้นเพื่อเป็น dependency ของ Holiday scope (shift) และของ `employees.work_location_id`** ซึ่งเดิมเป็นคอลัมน์ที่มีอยู่ในสคีมาแต่ไม่เคยมี master table รองรับมาก่อน (เหมือนกรณี `external_reference_no` ที่ wire ตอนทำ `StudentLoanReport`) — `employees.shift_id`/`work_location_id` ตอนนี้มี FK จริงแล้ว (`ON DELETE SET NULL ON UPDATE CASCADE`) และ dropdown ในหน้า Employee Detail ต่อ `data-api`/`select2-remote` แล้ว (เดิมเป็น native `<select>` ที่ไม่มี option ให้เลือกเลย)
- **Holiday** (`holidays` + `holiday_assignments`): assign หลายแบบพร้อมกันต่อ 1 รายการ (shift/department/position/employee) ผ่าน `assignment_mode` ('include'=whitelist / 'exclude'=blacklist ทุกคนยกเว้นที่เลือก) — mode='include' ต้องมีอย่างน้อย 1 scope, mode='exclude' ปล่อยว่างได้ (แปลว่าใช้ทั้งบริษัท) `holiday_assignments` ทั้งชุดถูก delete+reinsert ทุกครั้งที่ save (pattern เดียวกับ `approval_workflow_steps`) `scope_id` เป็น polymorphic เช็คที่ application layer ผ่าน `validateScopeRef()`
  - **Priority เมื่อ 2 holiday ที่ active ชนวันเดียวกันแต่ได้ผลลัพธ์ต่างกันสำหรับพนักงานคนเดียว: employee > position > department > shift** ทำใน `SetupRulesModel::resolveHolidaysForEmployee()` — **ยังไม่มี consumer จริง** (ไม่มีโมดูล attendance/payroll ไหนเรียกใช้ตอนนี้) แต่ build+test ไว้พร้อมแล้ว (`tests/holiday_test.php`) เหมือน pattern `ApprovalRequestModel` ตอนยังไม่ผูกกับ flow จริง
  - Date-collision check ตอน save เป็นแบบ **scope-blind** (เช็คแค่วันที่ชนกันไหม ไม่เช็คว่า scope จริงๆ overlap กันหรือเปล่า) เป็นการลดความซับซ้อนที่ตั้งใจ — full scope-aware overlap ให้ resolver ข้างบนจัดการตอน read แทน
  - `country_code` ของ holiday **ไม่ใช่ field ที่ผู้ใช้กรอกเอง** ระบบดึงจาก `companies.registered_country` อัตโนมัติตอน save เสมอ
- **Leave Type** (`leave_types` + `master_leave_categories` + `master_statutory_leave_minimums`): category เป็น master table (seed 10 ค่า: sick/personal/annual/maternity/ordination/military/leave_without_pay/family_parental/emergency/other) ตามด้วย field set สไตล์ HR SaaS มาตรฐาน — quota_type/amount/unit_type, requires_document, is_continuous (นับรวมวันหยุดในช่วงลาไหม), is_paid, allow_carry_over, gender_restriction, min_service_days, advance_notice_days, max_consecutive_days, applicable_employment_statuses (CSV ของ `employees.employment_status` ที่มีสิทธิ์ เช่น "permanent,contract" — ไม่ใช่ master table เพราะ enum นี้ fix อยู่แล้วในสคีมา ไม่ใช่ list ที่ต้องเพิ่มทีหลัง)
  - **`master_statutory_leave_minimums` เป็น global reference table (ไม่ผูกบริษัท)** ใช้แค่ validate ว่า `quota_amount` ของบริษัทต่ำกว่าขั้นต่ำตามกฎหมายของประเทศนั้นไหม — เช็คเฉพาะตอน `unit_type='day'` เท่านั้น (unit เป็นชม./ครึ่งวันข้ามไปเพราะเทียบกับเลขวันตรงๆไม่ได้) **ค่าที่ seed ไว้ตอนนี้มีแค่ TH annual(6 วัน)/maternity(98 วัน) และเป็น DRAFT ที่ยังไม่ verify กับตัวบทกฎหมายจริง** SG/MY ตั้งใจไม่ seed เพราะเป็น sliding scale ตามอายุงาน ใส่เลขเดียวจะผิดหลักกฎหมาย, US ไม่มี federal minimum เลยไม่ seed

- ทดสอบด้วย `tests/holiday_test.php` (24 assertions, เน้น priority engine) และ `tests/setup_rules_phase3_test.php` (24 assertions: Work Location CRUD, shift assignment replace-semantics, leave type CRUD + statutory-minimum validation)
- **RBAC** (`permissions`/`role_permissions`, ผูกกับ `structure_roles`/`employees.role_id` เดิม ไม่มี role/user_roles table ใหม่) — schema+seed (8 permissions) มาจาก phase 1, engine (`PermissionModel`) + matrix UI + enforcement ทำเพิ่มในรอบถัดมา ตาม scope ที่ตกลงไว้ (Holiday, Leave Type, Approval Workflow เท่านั้น — ไม่รวม Shift/Work Location)

  - **`allow_scope='own_department'` บังคับใช้จริงแค่ `approval_request.act` เท่านั้น** — Holiday/Leave Type เป็น company-wide config table ไม่มี concept "record นี้เป็นของแผนกไหน" ให้ scope filter ได้จริง ตอนนี้ทั้ง schema/matrix UI ยัง support เลือก scope ได้ทุก permission (เผื่ออนาคต) แต่ enforcement ปฏิบัติกับ Holiday/Leave Type เหมือน scope='all' เสมอไม่ว่าจะตั้งอะไรไว้ — เขียนอธิบายไว้ตรงๆใน `PermissionModel` docblock ไม่ปล่อยให้เข้าใจผิดว่า enforce ครบ
  - **UI**: เพิ่มเป็น tab ที่ 6 "Permissions" ใน Company Setup → Organizational Structure (ข้างๆ Branch/Role/Department/Position/Rank) เพราะ role ถูกจัดการอยู่ตรงนั้นแล้ว ไม่สร้างหน้าใหม่แยก (`public/js/setup/permission-matrix.js`) เป็น checkbox matrix ธรรมดา (permission เป็นแถว, role เป็นคอลัมน์) **ไม่ใช่ DataTable** เพราะเป็น grid ตายตัว 8 permission ไม่ใช่ record list ที่ต้อง paginate — cell ของ `approval_request.act` มี dropdown เล็กๆ โผล่มาเมื่อติ๊กแล้ว ให้เลือก All/Own Department บันทึกทั้ง matrix ทีเดียว (`saveMatrix()` ลบ `role_permissions` ทั้งหมดของทุก role ในบริษัทแล้ว insert ใหม่ตามที่ติ๊กไว้ — replace ทั้งชุดเหมือน pattern อื่นๆ ในโปรเจกต์ ไม่ diff ทีละแถว) ถ้าบริษัทยังไม่มี role เลยจะโชว์ empty state ชี้ไปที่แท็บ Role
  - ทดสอบด้วย `tests/permission_matrix_test.php` (23 assertions: isAdmin bypass, deny เมื่อไม่มี grant/ไม่มี role, matrix()/saveMatrix() replace-semantics, validation ของ role_id/permission_id ที่ไม่ถูกต้อง) — **enforcement ที่ controller layer ไม่ได้ทดสอบผ่าน HTTP แบบ deny-path จริง** เพราะ dev session hardcode `role: 'admin'` ไว้ตลอด (bypass ทุกครั้ง) ทดสอบแค่ที่ `PermissionModel` โดยตรงแทน ซึ่งครอบคลุม logic เดียวกับที่ controller เรียกใช้

## Team (Organizational Structure → 7th sub-tab "Team", `structure_teams`; also on Employee list/detail)
- **2026-08-24, explicit request: "ในหน้าตั้งค่าพนักงาน ให้เพิ่ม Team เข้าไปได้ด้วย (ในความหมายคือ เป็นบริษัทที่จ้าง outsource เพื่อไปอยู่กับหลาย Project...) ...ทีมให้เป็นการเพิ่มการตั้งค่าเช่นเดียวกับ Department แล้วดึงมาใช้ และเพิ่ม Filter ทีมในหน้า list พนักงานด้วย"** — the company running this app is itself an outsourcing/staffing firm; "Team" is the grouping of its own employees deployed together to one client/project, independent of their formal Department/Position in the firm's own org chart. Naming ("ทีม"/"Team", not "Project Team"/"Client Site") and whether it needs a client/scope field beyond code+name (yes) both confirmed via AskUserQuestion before building.
- **Schema**: `structure_teams` — same shape as `structure_departments` (`team_code`, `team_name_th`, `team_name_en`, per-company, soft-deletable, `uq_comp_team_code` unique on (comp_id, team_code, deleted_at) with the usual app-layer re-check per this project's own deleted_at+unique convention) plus one extra column `client_name` (free text, nullable, NOT split into _th/_en — a client's name isn't something that gets translated, same precedent as `structure_departments.cost_center` being a single free-text field). `employees.team_id` — nullable FK (`ON DELETE SET NULL ON UPDATE CASCADE`), placed right after `department_id`.
- **Backend is 100% additive to already-generic dispatchers, no new CRUD engine written**:
  - `CompanyProfileModel::structureConfig()` gained a `'team'` entry — the exact same generic `saveStructure()`/`deleteStructure()`/`isStructureValueDuplicate()` methods that already serve branch/role/department/position/rank handle Team with zero new code.
  - `CompanyProfileController::team()` (list, mirrors `department()`'s own `paginateData()` call verbatim) + `teamSave()`/`teamDelete()` (one-line dispatchers to `handleStructureSave('team')`/`handleStructureDelete('team')`, same as every other entity). Permission: reuses `company_structure.view`/`company_structure.manage` — no new permission key.
  - `MasterModel::master()` gained a `'team'` case in its existing generic table-driven select2-ajax resolver (just one row in `$tableMap`) — this is what `data-api="/api/team.get" data-type="team"` (Employee Detail's dropdown, Employee List's filter) actually calls.
  - Routes: `api/structure.team` (list), `api/structure.team.save`/`.delete`, `api/team.get` (dropdown options) — same naming pattern as department's equivalents.
- **Frontend (Organizational Structure tab)**: pill (`structure-tab-p7`/`data-page="p7"` — **appears BEFORE Permissions visually since the 2026-08-24 follow-up below, `data-page`/id left as "p7" on purpose, only the `<li>`'s DOM position moved, so `company-profile.js`'s `initStructure()` switch needed zero changes**) — `initStructure()`'s switch, `getStructureColumns('team')`, `formSchemas.team`, and `apiEndpointPrefix.team` in `company-profile.js` all follow the exact same schema-driven pattern department/position/rank already use (the Add/Edit modal's fields, validation, and payload are entirely driven by `formSchemas.team.fields` — no bespoke modal markup was written). `#tmpl-team-pane` mirrors `#tmpl-department-pane`'s table markup.

### v11 (2026-08-25, same-day bug report on v10's own Insert Symbol dropdown — "ตัว symbol ให้แสดงเป็น grid ครับ แล้วตอนนี้ปัญหาคือเปิด symbol แล้วกดปิดไม่ได้ครับ")
- **Real bug found and fixed, not a guess: the Symbol dropdown couldn't be closed once opened, and didn't render as a clean grid.** Root cause was a plain CSS specificity tie: `.ect-symbol-menu { display: grid; ... }` is a single-class selector — EXACTLY the same specificity (0,1,0) as Bootstrap's own base `.dropdown-menu { display: none; }` rule. A specificity tie is broken purely by cascade order (whichever rule is declared later in the page's combined stylesheet order wins), and this project's own `style.css` loads after `bootstrap.css`, so `display: grid` was winning the tie in BOTH states — meaning the element never actually reached `display: none` even after Bootstrap's JS correctly removed the `.show` class and tore down its Popper positioning on close. The dropdown was, in effect, permanently `display: grid` regardless of Bootstrap's own open/closed state, which is exactly "opens fine, but clicking to close does nothing" — Bootstrap's internal state was toggling correctly the whole time, only the CSS never reflected it.
- **Fix**: scoped both the hidden and shown rules to two-class selectors (`.dropdown-menu.ect-symbol-menu { display: none; }` / `.dropdown-menu.ect-symbol-menu.show { display: grid; ...same grid properties... }`) so this module's CSS is unambiguously MORE specific than Bootstrap's single-class default in both states, instead of depending on a cascade tie-break that a future stylesheet reorder/bundler change could just as easily flip back the other way. This single change fixes both complaints at once: the menu now reliably becomes invisible the instant Bootstrap removes `.show` (closing works), and — since the grid layout now only ever applies while genuinely shown, with nothing else fighting it for the `display` property — it renders as an unambiguous 8-column grid every time it opens.
- **No JS/schema changes needed** — `renderSymbolMenu()`/`addSymbolElement()`/the toggle handlers from v10 were already correct; this was purely a stylesheet cascade bug. Worth remembering as a category for this project: **any future custom CSS override on a Bootstrap-JS-driven component (dropdown/modal/collapse/etc.) that only differs by ONE class from Bootstrap's own selector is a latent tie-break bug** — always match or exceed Bootstrap's own selector specificity (e.g. pair the custom class with the component's base class, or with `.show`) rather than relying on load order.

- **Explicit request: "ในส่วนของ Request เพิ่ม Tab สำหรับการ Request ใบรับรองขึ้นมาด้วยคู่กับ Pay slip และการอนุมัติให้เป็นรูปแบบเดียวกับ Approve Process ครับมี timeline ให้กดดู"** — add a 3rd tab on the existing Payslip Requests page (`payslip-documents/requests`) for requesting an Employment Certificate, paired with the existing Payslip Requests tab, and restyle the approval detail view to look like the Payroll Approve Process page's timeline. Two AskUserQuestion decisions confirmed upfront: (1) approval **auto-generates the real PDF** (not just a status flag) — this is the recommended, chosen option, mirroring how Payslip Request auto-sends on approval; (2) the design upgrade applies to **BOTH** tabs (Payslip Requests' existing plain-list timeline gets upgraded too, not just the new Certificate tab).
- **`employment_certificate_requests`** (new table) is a direct structural port of `payslip_requests`' own paired-row architecture (see that model's docblock) — `comp_id`/`employee_id`/`language` (`th`/`en`)/`requested_by`/`approval_request_id` (unique, FK → `approval_requests`)/`status` (`pending`/`approved`/`rejected`/`cancelled`/`issued`/`issue_failed`)/`file_path`/`issue_error`. `EmploymentCertificateRequestModel::create()` validates the employee exists, the language is valid, no OTHER pending request already exists for that SAME employee+language (a pending request for the other language is NOT a duplicate — each language is issued/approved independently), **and confirms a real template already resolves for this employee+language via `EmploymentCertificateTemplateModel::resolveTemplateForEmployee()` before ever creating the row** — this is deliberate: a request must never be able to reach "approved" and then dead-end at issuance time because nobody set up a template, so the check happens up front at request time instead. Then inserts the row, calls the generic `ApprovalRequestModel::create($compId, 'EMPLOYMENT_CERTIFICATE_APPROVAL', $requestId, $label, $requestedBy)`, and links `approval_request_id` back — same one-owned-transaction pattern as `PayslipRequestModel::create()`. `EMPLOYMENT_CERTIFICATE_APPROVAL` was seeded config-only back in Employment Certificate Template's own v4 (see that section) with no consumer yet — this is its first real consumer, so any company that hasn't configured an ACTIVE workflow for this document type yet will get `create()` failing with "No active workflow is configured for this document type yet." (the generic engine's own message) until one is set up in Approval Workflow settings' 3rd pill.
- **Two-phase status, same pattern as Payslip Request's `approved`→`sent`/`send_failed`**: the generic engine's terminal verdict (`approved`/`rejected`/`cancelled`) is phase one; `EmploymentCertificateRequestModel::syncFromApprovalStatus()` (called from `ApprovalWorkflowController::syncDocumentAfterAct()`'s new `case 'EMPLOYMENT_CERTIFICATE_APPROVAL'`, kept OUT of `ApprovalRequestModel` itself to preserve its document-type-agnosticism) is phase two — on `approved` specifically, it calls a private `issuePdf()` which re-resolves the template (defensively — it could have been deleted between request and approval), renders via a new `EmploymentCertificateRenderer::renderForIssuance()`, writes the PDF to `public/uploads/employment_certificate_files/{comp_id}/{32-hex}.pdf`, and lands the row at `issued` (or `issue_failed` with a reason in `issue_error` on any handled failure — a rendering/disk error must never silently undo the approval decision itself, same "best-effort, wrapped in an outer catch" precedent as `PayslipDeliveryService::deliverForRequest()`). **Generated ONCE, at approval time, never re-rendered afterward** — a later edit to the employee's data or the template must not retroactively alter an already-issued legal document. `EmploymentCertificateRequestController::download()` streams the file back with `realpath()` path-containment validation (same pattern as every other file-serving endpoint in this app) and only for `status='issued'`.
- **Shared generic approval-detail timeline** (`public/js/setup/approval-request-detail.js`, new file) — extracted OUT of `payslip-request.js` (where the modal used to live as a plain bordered list) into its own file so BOTH the Payslip Requests tab and the new Employment Certificate Requests tab share ONE `#requestDetailModal` + ONE set of rendering functions, driven only by an `approval_request_id` and the generic engine's own endpoints (`GET api/approval-request.get`/`.logs`, `POST api/approval-request.act`) — **deliberately NOT modeled on `public/js/payroll/approval.js`'s own `.apv-*` timeline**, which is tightly coupled to `payroll_run_audit_logs`/`PayrollRunModel::approvalFlow()` and has no equivalent for an arbitrary `approval_request_id`. Same VISUAL language reused on purpose (colored circular stage marker + connecting line + title/badge/body, new `.art-*` CSS classes in `style.css`, deliberately a separate classname set since the shape is simpler — no per-approver "substep" concept) but oldest-stage-first (Requested at the top), not reversed like `.apv-*`, since it just appends each `approval_request_logs` row in the order the API already returns them. `openApprovalRequestDetail(id, onActed)` takes a reload callback so the caller's own DataTable can refresh itself after an approve/reject/cancel without this shared file knowing which table is open.
- **Employment Certificate Requests tab** (`public/js/setup/employment-certificate-request.js`, new file, `#tb_ecr_request`) mirrors `payslip-request.js`'s own DataTable structure — the one real UI difference is its status badge has 2 extra states (`issued`/`issue_failed`, Payslip's own equivalent is `sent`/`send_failed`) and its action column gets a Download button once `status='issued'`. **Initializes its DataTable only on `shown.bs.tab`, never immediately on page load** — unlike Payslip Requests (this page's default-active tab), this one starts hidden, and this app has hit the "`responsive: true` DataTable inside a `display:none` Bootstrap tab collapses every column to 0 width" bug enough times elsewhere that it's now a standing habit to check for on any non-default tab. The request-creation modal's employee picker reuses the existing generic `POST api/employee.report_to.get` endpoint as-is (same reuse precedent already established for Payslip/Employment Certificate Template's own "Assign To" pickers) rather than building a new one.
- **Page header generalized** — `requests.php`'s `.page-header-card-title`/`-desc` moved off the `payslip_requests` i18n key (that key is now ONLY the Payslip Requests tab button's own label) onto new dedicated `document_requests_title`/`document_requests_description` keys, so the page-level heading doesn't misword itself as payslip-only now that it covers two document types.
