## Approval Workflow (`Document & Approval` menu → "ลำดับผู้อนุมัติ"/"ติดตามสถานะ" tabs)
- Schema (8 ตาราง): `approval_document_types` (master, global, เพิ่ม document type ใหม่แค่ insert แถว — ตอนนี้มี `PAYROLL_RUN_APPROVAL`/`SLIP_REQUEST_APPROVAL`), `approval_workflows` (header ต่อบริษัท, soft delete), `approval_workflow_document_types` (join many-to-many), `approval_workflow_steps` (ลำดับ step — ตัวคอนฟิก **ไม่ได้เก็บผู้อนุมัติเอง** ดูข้อถัดไป), `approval_workflow_step_approvers` (ผู้อนุมัติของแต่ละ step, ดูข้อถัดไป), `approval_requests` (instance ที่กำลังวิ่ง/จบแล้ว), `approval_request_step_approvers` (persisted eligibility snapshot ต่อ request, ดูข้อถัดไป), `approval_request_logs` (audit trail รูปแบบเดียวกับ `payroll_run_audit_logs`)

  - **1 step มีผู้อนุมัติได้หลายคน** (`approval_workflow_step_approvers`: step_id, approver_type, approver_id — child table แยกจาก `approval_workflow_steps`, ผสม user เจาะจงกับ role ใน step เดียวกันได้ eligible pool = union ของทุก entry) — **`approver_id` เป็น polymorphic โดยตั้งใจ** คือ `employees.id` ถ้า `approver_type='user'`, หรือ `structure_roles.id` ถ้า `approver_type='role'` validate ที่ application layer ผ่าน `ApprovalWorkflowModel::validApproverRef()` (เช็ค comp_id ตรงกันด้วย กันเอา approver ข้ามบริษัทมาผูก) — `joint_approve_mode` ('any'/'all') ยังอยู่ระดับ step ควบคุมว่า pool ทั้งก้อนต้องอนุมัติร่วมกัน (any = คนแรกตัดสิน) หรือต้องครบทุกคน (all)
  - **Eligibility ถูก resolve ครั้งเดียวแล้ว persist ลง `approval_request_step_approvers`** (explicit request: "สร้างตารางเก็บรายการ Approve ของแต่ละ Process แล้วก็ดึงจากตารางนั้นว่าใครมีสิทธิ์ Approve บ้าง...ไม่ใช่ไปดึงข้อมูลใหม่ทุกรอบ") — resolve ทุก step ที่ active ตั้งแต่ตอนสร้าง request (ไม่ใช่ lazy ทีละ step แบบเดิม เพราะตอนนี้หลาย step อาจ actionable พร้อมกัน) เก็บ 2 column หลัก: `eligible_employee_ids` (คนที่มีสิทธิ์) กับ `acted_by` (คนที่อนุมัติจริง) — storage granularity ตาม `joint_approve_mode`: `'all'` = 1 แถวต่อคน (track รายคน), `'any'` = 1 แถวรวม (CSV ของทั้ง pool, ใครกดก่อนตัดสิน) ทุก read หลังจากนี้ (`canActOnRequest()`, `currentStepApprovers()`, `act()`) อ่านจากตารางนี้เท่านั้น ไม่ live-query role membership อีก (ยกเว้น `snapshotStepApprovers()` เองที่เป็นจุดเดียวที่ resolve สด)
  - **Sequencing เป็น per-step และตั้งอิสระ** (`requires_previous_step`, explicit request: "สามารถตั้งค่าได้แบบอิสระ เช่น 1 ก่อนค่อย 2 แต่ 3 อนุมัติได้เลยไม่ต้องรอ Step") — step ที่ `requires_previous_step=1` เข้าคิวตาม `step_order` ต้องรอทุก step ก่อนหน้าที่ก็ `requires_previous_step=1` เหมือนกัน "อนุมัติครบ" ก่อนถึงจะกดได้ (`ApprovalRequestModel::isStepUnlocked()`) — step ที่ `requires_previous_step=0` กดได้ทันทีเสมอไม่สนคิว ปุ่มฝั่ง UI ต้องโชว์อยู่แต่กดไม่ได้ตอน step ยัง lock (explicit request: "จะยังไม่เปิดปุ่มให้ แต่จะเห็นเป็นจุดๆ ว่าตัวเองอยู่ตำแหน่งไหน และตำแหน่งก่อนหน้านั้นอนุมัติหรือยัง")
  - **ผลรวมของ request ทั้งใบคำนวณจาก `group_type` ต่อ step** ('and'/'or'/'finish', port มาจาก origami's `getApprovalResult` แบบตัดส่วนที่ไม่เกี่ยวกับ payroll ทิ้ง — ไม่มี 'I' need-info status, ไม่มี level/project/customer/asset type) คำนวณใหม่หลังทุกการกระทำใน `ApprovalRequestModel::recomputeVerdict()`: **`and`** ทุก step กลุ่มนี้ต้องอนุมัติผลรวมถึงจะอนุมัติ มี step ไหนถูก reject = ทั้งใบ reject ทันที — **`or`** ถ้ามี OR step แค่ 1 step ผลของมัน**ไม่มีผลต่อการตัดสิน**เลย (ไม่ auto-pass, แค่ไม่นับ) ถ้ามี 2+ step แค่อนุมัติแล้ว 1 step ก็พอผ่าน ต้อง reject ครบทุก step ถึงจะ fail กลุ่มนี้ — **`finish`** พอ step นี้ถูกตัดสิน (อนุมัติหรือ reject) ผลนั้นกลายเป็นผลของทั้งใบทันที ไม่สนใจ step อื่นเลย แม้ step อื่นยังไม่ได้ตัดสินก็ตาม — reject ผ่าน engine นี้**ไม่ terminal เสมอไปอีกต่อไป** (OR-group reject อาจไม่จบทั้งใบถ้ายังมี OR step อื่นเหลือ) ดู `PayrollRunModel::reject()` ที่แก้ตามให้เช็ค `request_status` เหมือน `approve()` แล้ว
  - **`approval_requests.current_step_order` เป็น display-only แล้ว** ไม่ใช่ gating pointer อีกต่อไป (เพราะหลาย step อาจ actionable พร้อมกัน) — recompute เป็น step_order ต่ำสุดที่ยัง pending อยู่หลังทุกการกระทำ (`refreshCurrentStepOrderPointer()`) ไว้ให้ `list()`/`PayslipRequestModel`'s "current step" label มีอะไรโชว์
  - **`approval_workflow_steps` เป็น soft delete และแทนที่เฉพาะตอนคอนฟิกเปลี่ยนจริง** (explicit request: "ถ้ามีการ Save Request ใหม่ Approval Flow ต้องเปลี่ยน Flow เดิมให้ลบไปเลยถ้าไม่ใช่ข้อมูลเดิม แต่ต้องเป็น Soft Delete") — `save()` diff เนื้อหา steps ใหม่กับที่เก็บไว้ (ไม่สนใจ id, sort approvers ก่อนเทียบ) ถ้าเหมือนกันเป๊ะ **ไม่แตะอะไรเลย** (id เดิมอยู่ครบ ไม่มี churn) ถ้าต่างกัน soft-delete (`status='deleted'`, `deleted_by`, `deleted_at`) ชุดเดิมทั้งหมดแล้ว insert ชุดใหม่ — **`uq_workflow_step_order` unique constraint เดิมถูกถอดออกแล้ว** (เปลี่ยนเป็น index ธรรมดา) เพราะ step_order ซ้ำข้ามชุด active/deleted เป็นไปได้ปกติเมื่อไม่ hard delete แล้ว, app layer การันตีแค่ 1 active row ต่อ (workflow_id, step_order) จากการ insert ทั้งชุดพร้อมกันเสมอ — **`step_order` ยัง derive จากตำแหน่งใน array ฝั่ง client เสมอ** ไม่เชื่อค่าที่ client ส่งมาโดยตรง
