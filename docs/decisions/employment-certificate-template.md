## Employment Certificate Template (เมนู "หนังสือรับรองการทำงาน" → Settings, `employment-certificate/settings`)
- **2026-08-24, phase 1 ของ 3 (explicit request: "เพิ่มการตั้งค่าการจัดการรูปแบบ Employment Certificate ให้รองรับทั้งภาษาไทย และภาษาอังกฤษ รองรับการจัดตำแหน่งแบบอิสระ...เหมือน Word Photoshop...และเพิ่ม Tab การตั้งค่าการอนุมัติส่วนนี้ด้วย...และในเมนู Slip เงินเดือน อาจตั้งเป็นเมนูกลางๆ")** — งานมี 3 ส่วน (template designer / approval tab ใหม่ / รวมเมนู Payslip ให้เป็นเมนูกลาง) ถามผู้ใช้แล้วให้ทำ **แค่ template designer ก่อนในรอบนี้** — ส่วนที่ 2 (เพิ่ม pill ที่ 3 "อนุมัติหนังสือรับรองการทำงาน" ในหน้า Approval Workflow settings, ผูก document type ใหม่เข้า `ApprovalRequestModel`) และส่วนที่ 3 (generalize เมนู Payslip → เมนูขอเอกสารกลาง รองรับทั้ง payslip request และ cert request) **ยังไม่ได้ทำ** เป็น phase ถัดไป — **ไม่มี request/approval flow หรือการออกเอกสารจริงให้พนักงานเลยในรอบนี้** มีแค่หน้าออกแบบ template + endpoint preview เท่านั้น
- **Editor scope ที่ตกลงกับผู้ใช้แล้ว (ไม่ใช่เดารวมทุกอย่างจาก "เหมือน Word Photoshop")**: ลากตำแหน่งได้ + ปรับขนาดกล่องได้ + ปรับขนาดฟอนต์/การจัดวางซ้าย-กลาง-ขวา/ตัวหนา ต่อ element ได้ — **ไม่มี** color picker หรือเลือก font family หลายแบบ
- **แยกเลย์เอาต์ TH/EN กันคนละชุดเต็มรูปแบบ** (ตกลงกับผู้ใช้แล้ว) — คนละ template row, คนละชุด element, คนละโลโก้ที่ upload ได้อิสระต่อภาษา (ไม่ใช่ตำแหน่งเดียวกันแค่สลับข้อความเหมือน `payslip_templates.language_mode='both'`)
- Schema (3 ตาราง ใหม่ทั้งหมด ไม่แตะ `payslip_templates`/`payslip_template_fields` เดิมเลย): `master_employment_certificate_field_types` (global master, 15 fields, mirror `master_payslip_field_types` — seed ครอบคลุม company_logo/company_name/company_address/company_tax_id/company_signatory/employee_no/employee_name/position/department/employment_date/employment_status/employment_type/base_salary/issue_date/static_text), `employment_certificate_templates` (**1 row ต่อ comp_id+language เท่านั้น** ไม่ใช่หลาย template ให้เลือกเหมือน payslip — ไม่มี concept "เลือก template ไหนเป็น default" เลย เพราะมีแค่ 1 ต่อภาษาอยู่แล้ว, มี `logo_path` แยกต่อ template เหมือน payslip เพราะ `companies` ไม่มีคอลัมน์ logo), `employment_certificate_template_elements` (**ตำแหน่ง/ขนาดเก็บเป็น percentage (0-100) ของหน้า A4 ไม่ใช่ px/pt/mm** — ตั้งใจ เพื่อให้ canvas ฝั่ง browser กับ dompdf renderer ฝั่ง server ใช้ coordinate space เดียวกันเป๊ะๆ ไม่ต้องแปลงหน่วยเลย ป้องกัน WYSIWYG เพี้ยน)
  - **Element มีแค่ 2 ชนิด: `text` กับ `image`** ไม่มี "field box" แยกประเภทต่างหาก — `text` element มี `content` เป็นข้อความอิสระที่ฝัง token `{{field_key}}` ได้ตรงไหนก็ได้ (เช่น `{{employee_name}}` เดี่ยวๆ = กล่องข้อมูลล้วน, หรือฝังกลางประโยคแบบ "ขอรับรองว่า {{employee_name}} ดำรงตำแหน่ง {{position}}..." ก็ได้) — **นี่คือกลไก "Auto Replace" ที่ผู้ใช้ขอ** ไม่ใช่ mail-merge แบบ rich text ซับซ้อน แค่ string substitution ธรรมดาตอน generate เท่านั้น `image` element รองรับแค่ `field_key='company_logo'` (แหล่งรูปเดียวที่มีตอนนี้)
  - `save()` (`EmploymentCertificateTemplateModel::save()`) **แทนที่ element ทั้งชุดทุกครั้ง** (delete+reinsert) ไม่ใช่ diff-and-skip-if-unchanged แบบ Approval Workflow steps — เพราะ template เป็นองค์ประกอบเชิงพื้นที่ (spatial composition) แก้ทั้งชุดพร้อมกันเสมอ ไม่มี in-flight state ใดๆ ผูกกับ element id เหมือน approval step ที่ request ที่ยัง pending ต้อง snapshot step_order ไว้ — auto-create template header ตอน save() ครั้งแรกของแต่ละภาษา (ไม่มีปุ่ม "สร้าง template" แยกต่างหาก)
- Backend: `EmploymentCertificateTemplateModel` (`fieldTypeOptions()`, `getByLanguage()`, `save()`, `isValidLogoPath()` static — เหมือน `PayslipTemplateModel::isValidLogoPath()`), `EmploymentCertificateTemplateController` (`get`/`save`/`uploadLogo`/`preview`, permission เดียว `employment_certificate_template.manage` แบบเดียวกับ `payslip_template.manage` — ไม่แยก view/manage), `EmploymentCertificateRenderer` (`app/services/`, ไม่ใช่ `app/services/reports/` เพราะไม่ใช่ Reports module — ไม่มี report code/ReportRegistry เกี่ยวข้อง) ใช้ `PdfRendererTrait` ตัวเดียวกับ Reports module (dompdf, DejaVu Sans font) `buildHtml()` วาง `<div style="position:absolute;left:X%;top:Y%;width:W%;height:H%;...">` ต่อ element ลงใน container `.cert-page { width:210mm; height:297mm; }` — coordinate space เดียวกับ browser canvas เป๊ะ
  - **`{{field_key}}` substitution ทำผ่าน `htmlspecialchars()` เนื้อหาทั้งกล่องก่อน แล้วค่อย str_replace token ด้วยค่าที่ escape แล้วอีกที** (`{{`/`}}` ไม่ใช่ HTML special char เลยรอดจาก escape รอบแรกได้ครบ) ป้องกัน XSS จากทั้งข้อความที่ admin พิมพ์เองและค่าจริงของพนักงาน/บริษัทที่ดึงมาแทน
  - Preview (`POST /api/employment-certificate-template.preview`) render **canvas ปัจจุบันที่ยังไม่ได้ Save** เหมือน pattern ของ payslip-template.preview เป๊ะ (คืน PDF binary ตรงๆ, frontend ใช้ `fetch()` เช็ค Content-Type ไม่ใช่ `$.ajax`) — ข้อมูลบริษัทใช้ของจริงจาก DB, ข้อมูลพนักงานใช้พนักงานจริงคนแรกของบริษัทถ้ามี (`fetchAnyEmployee()`) ไม่งั้น fallback เป็น mock ("สมชาย ใจดี"/"Somchai Jaidee") — ยังไม่รองรับเลือกพนักงานเฉพาะเจาะจงมา preview (ไม่มี employee picker ในหน้านี้ตอนนี้)
  - Logo upload: pattern เดียวกับ `PayslipTemplateController::uploadLogo()` ทุกอย่าง (finfo MIME check, 2MB limit, jpg/png/svg เท่านั้น, random 32-hex filename) แค่เปลี่ยน path เป็น `public/uploads/employment_cert_logos/{comp_id}/` (`.gitignore`'s `public/uploads/` ครอบอยู่แล้ว ไม่ต้องเพิ่ม)
- Frontend: canvas drag/resize **เขียนเองด้วย plain mouse events ทั้งหมด ไม่เพิ่ม dependency ใหม่** (เช็คแล้วโปรเจกต์นี้ไม่มี jQuery UI/interact.js อยู่แล้ว และ bounding-box drag+resize ธรรมดาไม่จำเป็นต้องพึ่ง library) `public/js/setup/employment-certificate-template.js` เก็บ `elements[]` เป็น source of truth ต่อภาษาที่กำลังเปิดอยู่ (สลับภาษา = reload ใหม่ทั้งหมด ไม่เก็บ state ข้ามภาษา) double-click กล่อง text เพื่อแก้ content (modal เล็ก พร้อม token hint) กล่อง image แสดงแค่ไอคอน placeholder บน canvas (โลโก้จริงเห็นตอน Preview/PDF เท่านั้น ไม่ได้ render รูปจริงลง canvas เพื่อความง่าย)
- เมนู: เพิ่มเมนูใหม่ "หนังสือรับรองการทำงาน" แยกจากเมนู "สลิปเงินเดือน" **โดยตั้งใจ** (ยังไม่รวมตามที่ผู้ใช้เสนอไว้สำหรับ phase ถัดไป) ใช้ไอคอน REPORT.svg ซ้ำ (ไม่มีไอคอน certificate เฉพาะ) เป็น menu-item เดี่ยวไม่มี submenu (มีแค่หน้าเดียวตอนนี้ พอมี Requests/Approval ใน phase ถัดไปค่อยเปลี่ยนเป็น submenu)
- Permission ใหม่ 1 ตัว: `employment_certificate_template.manage` (seed เข้า `permissions` table แล้ว จะโผล่ใน Permission Matrix อัตโนมัติเพราะ matrix query permissions ทั้งหมดแบบ dynamic ไม่ได้ hardcode รายการ)
- ทดสอบด้วย `tests/employment_certificate_template_test.php` (74 assertions ในเวอร์ชันปัจจุบัน หลังรวม v2 ด้านล่าง — ยืนยันได้แค่ PDF ไม่ error/มีเนื้อหาที่ถูก substitute จริง/embed font ที่ถูกต้องจริง ไม่ได้ verify การจัดวางภาพแบบ pixel-perfect ในตัว PDF เพราะไม่มี PDF rasterizer ในสภาพแวดล้อมนี้)

### v2 (2026-08-24, explicit follow-up request เดียวกันวัน: "ให้รองรับหลาย Template และมี Template มาตรฐานให้เลือกใช้งาน สัก 2-3 แบบ...ให้ตั้งค่าหน้ากระดาษได้...เพิ่มให้ Upload รูปภาพมาใช้งานเองได้...ใน Mode Preview ให้ตั้งค่าได้ว่าจะใส่ลายน้ำ...PDF ให้รองรับภาษาไทยด้วย...ตรง Add to Canvas ให้สามารถลากลงไปวางได้...สามารถเลือก Front ได้ ทั้งรูปแบบขนาดและสี ตัวหนาตัวบางตัวเอียง...เหมือน Word")
- **บั๊กจริงที่เจอและแก้ระหว่างทำ: dompdf ไม่รองรับภาษาไทยเลยที่ผ่านมา** — ตรวจสอบด้วยการ parse `cmap` table ของฟอนต์ `DejaVuSans*.ttf` ที่ bundle มากับ dompdf โดยตรง (ไม่ใช่การเดา) พบว่า **ไม่มี glyph ภาษาไทยแม้แต่ตัวเดียว** ทั้ง DejaVu Sans/Serif/Sans Mono ขัดกับ docblock เดิมของ `PdfRendererTrait` ที่สันนิษฐานว่า DejaVu Sans รองรับไทย — แปลว่า PDF ภาษาไทยทุกฉบับที่ระบบเคย generate ผ่าน trait นี้ (Reports/Payslip module ทั้งหมด) มีโอกาสสูงมากที่ glyph ภาษาไทยจะหายไปหมด **ยังไม่ได้แก้ `PdfRendererTrait` เอง** (ตั้งใจ — out of scope ของ request รอบนี้ที่พูดถึง Employment Certificate โดยเฉพาะ, การเปลี่ยน default font ของทุก statutory export ที่มีอยู่ต้องพิจารณาแยกต่างหาก) แค่ flag ไว้ชัดเจนใน `storage/fonts/thsarabun/NOTICE.md` และที่นี่
  - **แก้เฉพาะ `EmploymentCertificateRenderer`**: bundle ฟอนต์ **TH Sarabun New** (4 ทรง: normal/bold/italic/bolditalic) ไว้ที่ `storage/fonts/thsarabun/` (สัญญาอนุญาต SIL Open Font License — ฟอนต์มาตรฐานราชการไทยจาก SIPA ใช้ซ้ำ/แจกจ่ายได้ฟรี) register เข้ากับ dompdf runtime ผ่าน `Dompdf\FontMetrics::registerFont()` (`registerThaiFonts()`, เรียกทุกครั้งก่อน render — cache-hit ทำให้ไม่ copy ไฟล์ซ้ำหลังครั้งแรก) — **ตั้งใจไม่ bundle Tahoma/Leelawadee** แม้ตรวจแล้วว่ามี glyph ไทยครบเหมือนกัน เพราะเป็นฟอนต์ลิขสิทธิ์ของ Microsoft ที่มากับ Windows ไม่ใช่ของฟรีที่แจกจ่ายซ้ำได้ ห้าม commit เข้า repo
  - **บั๊กที่ 2 ที่เจอระหว่างแก้บั๊กแรก**: `registerFont()` ของ dompdf ต้องได้ path แบบ `file://` (ไม่ใช่ path เปล่า — protocol เปล่าไม่อยู่ใน `allowed_protocols`) และต้องอยู่ภายใต้ `Options::chroot` ของ dompdf (default = แค่โฟลเดอร์ vendor ของ dompdf เอง) — ต้อง `$options->setChroot([โปรเจกต์ root ทั้งหมด])` ก่อนถึงจะ register ฟอนต์จาก `storage/fonts/` หรือ embed `<img>` จาก `public/uploads/` ได้เลย (เจอจริงผ่านการ debug ทีละ step ด้วย reflection ไม่ใช่เดา) ปลอดภัยเพราะ `isRemoteEnabled` ยัง false เสมอ (บล็อก remote http/https อยู่ดี) และทุก path ที่มาถึงจุดนี้ผ่านการ validate มาแล้วจาก `isValidLogoPath()`/image-library lookup ไม่ใช่ user input ดิบ
  - **บั๊กที่ 3 (สำคัญที่สุด, ตัวที่ทำให้ font-family/color/italic/underline ไม่ทำงานเลยตอน render จริง)**: element style string ใช้ double quote ล้อมค่า font-family (`font-family:"TH Sarabun New"`) ซ้อนอยู่ข้างในของ `style="..."` ที่เป็น double quote เหมือนกัน — HTML attribute แตกกลางคัน ทำให้ CSS property ทุกตัวหลัง font-family (color, font-family เอง) หายไปเงียบๆ ไม่มี error ใดๆ dompdf fallback ไปใช้ Times-BoldItalic แทนโดยไม่บอกอะไรเลย — แก้โดยเปลี่ยนเป็น single quote ล้อม font-family (`font-family:'TH Sarabun New'`) เพราะซ้อนอยู่ใน double-quoted attribute (ดู `EmploymentCertificateRenderer::buildHtml()` comment ตรงจุดนี้ + assertion เฉพาะใน test ที่ล็อกพฤติกรรมนี้ไว้กันเจอซ้ำ)
- **Multi-template**: ถอด "1 template ต่อภาษา" ของ v1 ออก เปลี่ยนเป็นหลาย template ต่อภาษาได้ (แบบเดียวกับ `payslip_templates`) `is_default` บังคับ single-active-per-(comp_id,language) ที่ application layer — template แรกที่ save ของแต่ละภาษากลายเป็น default อัตโนมัติ (ไม่งั้นจะไม่มี default เลยจนกว่าจะตั้งเอง) ตัวถัดไปไม่auto-default
  - **Template มาตรฐาน 3 แบบ + blank** (`EmploymentCertificateTemplateModel::presetElements()`, PHP-defined ไม่ใช่ DB row เพราะไม่ใช่ system-owned data ที่ต้อง sync) — `classic` (จัดกลางทางการ), `modern` (โลโก้มุมซ้ายบน), `minimal` (ข้อความล้วน) เลือกตอนสร้าง template ใหม่ผ่าน modal ปรับแก้อิสระได้ทุก element หลังสร้างเหมือน template ที่สร้างเองปกติ ไม่ใช่ "locked layout"
  - CRUD ครบตามแบบ `PayslipTemplateModel`: `list()`/`get()`/`getDefault()`/`save()` (มี `id` = update ในที่, ไม่มี = สร้างใหม่)/`duplicate()`/`delete()` (soft)/`setDefault()`
- **Page setup**: เพิ่ม `page_size` (A4/Letter/Legal) + `orientation` (portrait/landscape) ต่อ template — `EmploymentCertificateRenderer::pageDimensionsMm()` map เป็น mm จริง สลับ width/height เมื่อ landscape, ใช้ทั้งใน `@page` CSS (browser canvas กับ PDF ใช้เลขเดียวกันเป๊ะ) และใน `dompdf->setPaper([0,0,widthPt,heightPt])` (ใช้ explicit point array แทน named size string เพื่อให้ตรงกับเลข mm ที่คำนวณเองเป๊ะๆ ไม่พึ่ง dompdf's built-in Letter/Legal ที่อาจปัดเศษต่างกัน)
- **คลังรูปภาพใช้ซ้ำได้** (`employment_certificate_images`, company-wide ไม่ผูกกับ template/ภาษาใดภาษาหนึ่ง) — upload ครั้งเดียว วางซ้ำได้ทุก template ผ่าน element `image_asset_id` (แยกจาก `field_key='company_logo'` ที่ยังผูกกับ `logo_path` ของแต่ละ template เหมือนเดิม) `deleteImage()` เป็น **hard delete** (ต่างจาก convention soft-delete ทั่วไปของโปรเจกต์ — ตั้งใจ เพราะรูปในคลังไม่มีความหมายเชิง audit/compliance แบบข้อมูล payroll) แต่ **บล็อกถ้ายังมี template ไหนอ้างอิงอยู่** (FK เป็น `ON DELETE SET NULL` แต่ตั้งใจไม่ปล่อยให้ orphan เงียบๆ โดยไม่บอก admin) ต้องเอา element ออกจากทุก template ก่อนถึงจะลบไฟล์จริงได้ — canvas (ตัว editor) โชว์แค่ icon placeholder สำหรับทุก image element เหมือนเดิม (ทั้ง logo และรูปจากคลัง) รูปจริงเห็นตอน Preview/PDF เท่านั้น เพื่อความง่าย ไม่ต้องโหลด/cache รูปจริงในหน้าออกแบบ

### v11 (2026-08-25, same-day bug report on v10's own Insert Symbol dropdown — "ตัว symbol ให้แสดงเป็น grid ครับ แล้วตอนนี้ปัญหาคือเปิด symbol แล้วกดปิดไม่ได้ครับ")
- **Real bug found and fixed, not a guess: the Symbol dropdown couldn't be closed once opened, and didn't render as a clean grid.** Root cause was a plain CSS specificity tie: `.ect-symbol-menu { display: grid; ... }` is a single-class selector — EXACTLY the same specificity (0,1,0) as Bootstrap's own base `.dropdown-menu { display: none; }` rule. A specificity tie is broken purely by cascade order (whichever rule is declared later in the page's combined stylesheet order wins), and this project's own `style.css` loads after `bootstrap.css`, so `display: grid` was winning the tie in BOTH states — meaning the element never actually reached `display: none` even after Bootstrap's JS correctly removed the `.show` class and tore down its Popper positioning on close. The dropdown was, in effect, permanently `display: grid` regardless of Bootstrap's own open/closed state, which is exactly "opens fine, but clicking to close does nothing" — Bootstrap's internal state was toggling correctly the whole time, only the CSS never reflected it.
- **Fix**: scoped both the hidden and shown rules to two-class selectors (`.dropdown-menu.ect-symbol-menu { display: none; }` / `.dropdown-menu.ect-symbol-menu.show { display: grid; ...same grid properties... }`) so this module's CSS is unambiguously MORE specific than Bootstrap's single-class default in both states, instead of depending on a cascade tie-break that a future stylesheet reorder/bundler change could just as easily flip back the other way. This single change fixes both complaints at once: the menu now reliably becomes invisible the instant Bootstrap removes `.show` (closing works), and — since the grid layout now only ever applies while genuinely shown, with nothing else fighting it for the `display` property — it renders as an unambiguous 8-column grid every time it opens.
- **No JS/schema changes needed** — `renderSymbolMenu()`/`addSymbolElement()`/the toggle handlers from v10 were already correct; this was purely a stylesheet cascade bug. Worth remembering as a category for this project: **any future custom CSS override on a Bootstrap-JS-driven component (dropdown/modal/collapse/etc.) that only differs by ONE class from Bootstrap's own selector is a latent tie-break bug** — always match or exceed Bootstrap's own selector specificity (e.g. pair the custom class with the component's base class, or with `.show`) rather than relying on load order.

### v12 (2026-08-25, same-day bug report — "เพิ่มหน้า 2 3 แล้วใน preview ไม่ขึ้น และใน 1 object ใน Add to Canvas ดึงได้แค่ครั้งเดียว ลากรอบที่ 2 ไม่ลง")
- **Real bug found and fixed, not a guess: `elementsPayload()` never sent `page_number` to the server at all.** This is the single function BOTH Save and Preview build their request body from — it listed every other element property explicitly but omitted `page_number` completely, so no matter which page an element was actually placed on in the editor, it silently reverted to the server's own default of page 1 the instant it was serialized (`EmploymentCertificateTemplateModel::validateElements()` falls back to `1` whenever the field is absent from the payload, by design — that fallback exists for backward compatibility with pre-multi-page templates, not to be hit by brand-new elements that DO have a real page). Placing elements on page 2/3 and hitting Preview looked exactly like "the new pages don't show up" — nothing was actually missing; every element was quietly collapsing back onto page 1 before the request ever left the browser. **This also silently affected every Save, not just Preview** — any template saved with multi-page content before this fix has every element persisted as `page_number=1` regardless of which page it was designed on; a future session investigating "my pages disappeared after I reloaded" on an existing template should check for exactly this. Fixed by adding `page_number: e.page_number || 1` to the mapped object in `elementsPayload()` — the in-memory value was already being tracked correctly by `emptyElementBase()`/`currentPageElements()`/the page navigator from v10, only this one serialization step was dropping it.
- **Real bug found and fixed: the Company Logo palette item could only ever be dropped once, anywhere in the whole template (not just the current page).** `addElementFromPalette()` had a special case for `code === 'company_logo'`: before creating a new element, it searched `elements` for an ALREADY-PLACED company_logo image element across every page, and if one existed anywhere, it just re-selected that existing element instead of creating a new one — so a second drag (e.g. wanting the logo on page 3 too, now that multi-page documents exist) silently did nothing visible; focus just jumped back to the original logo element on its original page. No other palette item had this restriction — every text/other-image field already created a fresh element on every drop. This restriction predates multi-page documents (existed since v1's single-language-single-page days, when a single template only ever had one obvious place for one logo) and simply never got revisited when multi-page landed in v10.
- Both fixes are pure client-side JS — no schema/model/renderer changes were needed since the backend already handled `page_number` and unlimited duplicate elements correctly (confirmed: `tests/employment_certificate_template_test.php`'s v10 multi-page/shape/table section calls `EmploymentCertificateTemplateModel::save()` directly with `page_number` already present in the raw element array, bypassing this exact JS layer — which is why the existing 182 assertions didn't catch either bug).
