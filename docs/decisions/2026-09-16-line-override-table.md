# Adjustments modal → tab "ปรับตัวเลข" รวมเป็นตารางเดียว + checkbox ความหมายบวก (2026-09-16)

## ของเดิม: 2 UI สำหรับเรื่องเดียวกัน

tab นี้เคยมี 2 ส่วนซ้อนกัน:

1. **panel "ไม่นำมาคำนวณสำหรับพนักงานคนนี้"** — checklist ทั้ง catalog ของบริษัท (ติ๊ก = ยกเว้น)
   + ปุ่มบันทึกของตัวเอง
2. **การ์ดต่อรายการ** — 1 การ์ด/1 รายการที่คำนวณได้จริง แต่ละใบมี input จำนวนเงิน + checkbox
   "ยกเว้นรอบนี้" + ปุ่ม **บันทึกของตัวเอง** + ปุ่ม "คืนค่าที่คำนวณได้"

**ทั้งสองเขียน field เดียวกันผ่าน endpoint เดียวกัน**: `payroll_run_line_overrides` (run_id, employee_id,
item_code, `action='exclude'`) ผ่าน `api/payroll-run.line-override.save`/`.remove` — คอมเมนต์ในโค้ดเดิมเอง
ก็ระบุไว้ว่า *"just a faster, bulk way to set it, not a separate concern"* → เป็น **แนวคิดเดียว 2 หน้าตา**
จึงยุบเหลือตารางเดียว

## สิ่งที่เสียไปจากการยุบ panel (ยอมรับแล้ว)

panel ลิสต์ catalog ทั้งบริษัท จึง**ยกเว้นล่วงหน้า**รายการที่พนักงานคนนี้ยังไม่มีบรรทัดคำนวณได้
ส่วนตารางใหม่ลิสต์เฉพาะสิ่งที่ผลคำนวณล่าสุดมีจริง (+ รายการที่ถูกยกเว้นจนหลุดออกจาก breakdown ซึ่งยังโชว์อยู่
เพื่อให้กดคืนได้)

- **ปกติเป็น no-op** — ยกเว้นรายการที่ไม่ได้ถูกคำนวณอยู่แล้ว ไม่เปลี่ยนยอดอะไรเลย
- **เคสที่เสียจริง (แคบ)**: ถ้าภายหลังมีข้อมูลทำให้รายการนั้นโผล่เข้ามา (เพิ่ม PED assignment / manual line
  แล้วคำนวณใหม่) การยกเว้นล่วงหน้าจะมีผลทันทีโดยไม่ต้องกลับมากดอีก — ตอนนี้ต้องรอให้รายการโผล่ก่อนแล้วค่อยติ๊กออก
- **เคสที่ 2 ที่หายไปพร้อมกัน (เห็นจากการทดสอบจริง)**: รายการที่ถูกปิดไว้ที่ Run Settings **และไม่มี override
  ส่วนตัว** จะหายจาก tab นี้ทั้งแถวหลังคำนวณรอบถัดไป (ไม่อยู่ใน breakdown แล้ว และ fallback list เก็บเฉพาะ
  รายการที่มี override ส่วนตัว) — ก่อนหน้านี้ panel ยังโชว์มันเป็นแถวเทาติ๊กค้างไว้ · ระหว่างที่ยังไม่ได้
  คำนวณใหม่ แถวยังอยู่และแสดงเป็น ☐ disabled + tooltip ตามสเปก · ที่เดียวที่เห็นภาพรวมว่ารอบนี้ปิดอะไรไว้บ้าง
  คือ panel Run Settings ของรอบเอง ซึ่งเป็นที่ที่แก้ค่านั้นได้จริงอยู่แล้ว
- **เหตุผลที่ยอมรับ**: ราคาของการมี 2 UI ที่เขียนค่าเดียวกัน (ผู้ใช้ต้องรู้เองว่าติ๊กที่ไหนก็ได้ผลเท่ากัน,
  สถานะ 2 ที่ต้องตรงกันเสมอ, ปุ่มบันทึก 2 ปุ่มในหน้าจอเดียว) สูงกว่าเคสข้างบนที่เกิดน้อยและมีทางทำอ้อมได้
- `itemChecklistBoxesHtml()` **ไม่ถูกลบ** — panel Run Settings ระดับรอบ (`#runSettingsItemChecklist`)
  ยังใช้ฟังก์ชันเดียวกันนี้อยู่

## checkbox เป็นความหมายบวกทั้ง tab

☑ = **นำมาคำนวณ** · ☐ = ไม่นำมาคำนวณ — ของเดิมกลับกัน (ติ๊ก = ยกเว้น) ซึ่งอ่านแล้วต้องแปลในหัวทุกครั้ง

**backend ไม่เปลี่ยนเลย** — ยังเป็น "มีแถว `action='exclude'` = ถูกยกเว้น" เหมือนเดิม การกลับความหมายเกิดที่
ขอบเดียวคือ `lineOverrideRowPlanRd()` (detail.js):

| สภาพใน UI | ส่งอะไร |
|---|---|
| ☐ (และเดิมไม่ได้ถูกยกเว้น) | `save action='exclude'` |
| ☑ + กรอก/แก้ "ค่าใหม่" | `save action='override_amount'` |
| ☑ + ช่องว่าง (และเดิมมี override อยู่) | `.remove` |
| ไม่ต่างจากตอนโหลด | ไม่ยิงอะไรเลย |

แถว statutory ยิงไป `api/payroll-run.statutory-line-override.*` ซึ่ง **wrap `item_code` เองที่ server**
(client ห้าม wrap — เป็นกฎเดิมที่ยังคงอยู่)

**ช่อง "ค่าใหม่" ของแถวที่มี override อยู่แล้วจะถูก prefill ด้วยค่านั้น** ไม่ปล่อยว่าง: ค่านั้นคือค่าที่มีผลจริง
อยู่ ณ ตอนนี้ ถ้าปล่อยว่างผู้ใช้จะมองไม่เห็นว่ามี override ค้างอยู่ และคำว่า "ว่าง = ไม่เปลี่ยน" จะมี 2 ความหมาย
คนละแบบบนแถวคนละชนิด — **การล้างช่องให้ว่างจึงเป็น "คืนค่าที่ระบบคำนวณ" ของแถวนั้นในตัว** (แทนปุ่มคืนค่ารายแถวเดิม)

## แถวที่ถูกปิดไว้ที่ Run Settings

`payroll_run_item_exclusions` (ระดับรอบ ไม่มี employee_id) → แถวนั้น ☐ + **disabled ทั้ง checkbox และช่องค่าใหม่**
+ tooltip "ปิดไว้ที่ Run Settings ของรอบ — เปิดได้ที่ Run Settings" · **ไม่เปิดทาง override_amount ใน UI**
ทั้งที่ backend ทำได้ (ใส่จำนวนเงินให้รายการที่รอบปิดไว้ = ดึงกลับเข้ามาเฉพาะคนนี้ ตาม `recalculate()`'s
resolution) — เพราะเป็นทางลัดที่ขัดกับสิ่งที่หน้าจอเพิ่งบอกไปว่า "ปิดอยู่" · disabled เฉพาะแถวที่ **ไม่มี**
override ส่วนตัวอยู่แล้ว (ถ้ามี override อยู่ ตัว override ชนะระดับรอบเสมอ แถวนั้นจึงยังแก้ได้)

## ปุ่มบันทึก: จาก N ปุ่ม เหลือ 1 ที่ footer

ปุ่มบันทึกรายการละปุ่มหายหมด — ปุ่ม "บันทึก" ของ modal (dispatcher เดิม) บันทึกทุกแถวที่เปลี่ยน
**ยิงทีละแถวเรียงกัน** เพราะ backend ไม่มี endpoint แบบ batch และ `lineOverrideSave()` เองจบด้วย
`recalculate()` ทั้งรอบทุกครั้ง (ยิงพร้อมกันจะได้ recalculate 2 ตัวเขียนทับกัน) — ระหว่างทาง footer ขึ้น
"กำลังบันทึก i/N…" และ **ล็อกทั้ง modal**; แถวไหนล้ม **หยุดทันที** แล้วรายงานชื่อแถวนั้น + จำนวนที่บันทึกสำเร็จ
ไปแล้ว; จบแล้ว refresh ครั้งเดียว (ทั้งกรณีสำเร็จและล้ม เพราะแถวที่ผ่านไปแล้วถูกบันทึกจริง)

endpoint `save-batch` ที่เขียนทุกแถวแล้ว recalculate **ครั้งเดียว** = งาน Batch 5 → `docs/specs/line-override-batch.md`

tab นี้เป็น tab แรกที่ dispatcher เรียก **ฟังก์ชันตรง** (`saveFn`) แทนการกดปุ่มที่ซ่อนไว้ — อีก 3 tab ยังเป็น
`saveSelector` (ปุ่มซ่อน) ตามเดิม บันทึกไว้ใน BACKLOG ให้ตามเก็บ

## แถวที่ระบบข้ามโดยการตั้งค่า: ซ่อนไว้ก่อน กด "แสดง" ได้

`StatutoryCalculationEngine` สร้างบรรทัดครบ **ทุก item ที่บริษัทเปิดใช้ ให้พนักงานทุกคน** เสมอ — คนที่ไม่เข้า
เงื่อนไขได้บรรทัด 0.00 + `note` บอกเหตุผล (ตรวจจริง: comp 1 เปิด TH_SSO/TH_PIT/TH_PVD → ทุกคนได้ 3 บรรทัด ·
EM009 `pvd_enrolled=0` → PVD 0.00 `employee_not_enrolled` ทั้งที่บริษัทตั้งอัตรา PVD ไว้ 3%)

**เกณฑ์ซ่อนไม่ใช่ "ยอด = 0"** เพราะ 0.00 มี 2 ความหมาย: PIT = 0 เพราะรายได้ไม่ถึงเกณฑ์ (ผลคำนวณจริง ควรเห็น
และ override ได้) กับ PVD = 0 เพราะไม่ได้เข้ากองทุน (ไม่ได้คำนวณเลย) — ตัวที่แยกออกคือ `note` ซึ่งมีอยู่ใน
`statutory_breakdown` แล้ว จึงส่งออกมาเป็น read-only field (แบบเดียวกับ `item_type`)

- **ซ่อน** เมื่อ `note ∈ {employee_not_enrolled, employee_tax_exempt, disabled}` **และไม่มี override ส่วนตัว**
- **ห้ามซ่อน**: `no_rate_configured` / `no_rate_ever_configured` / `unrecognized_calc_base` (ตั้งค่าขาด —
  ซ่อนแล้วจะกลบปัญหา; ตัวแรกทำให้ `calc_status` เป็น error อยู่แล้ว) และ `manually_overridden` /
  `manually_excluded` (มีคนจัดการไปแล้ว) — override เขียนทับ note เป็น `manually_overridden` เสมอ กฎเดียวนี้
  จึงพอ ไม่มีทางที่แถวที่มี override จะถูกซ่อน
- ใต้ตารางมีบรรทัดเดียว `--fs-sm` เทา "ซ่อน N รายการที่ไม่ใช้กับพนักงานคนนี้ · แสดง" (N = 0 → ไม่มีบรรทัด) ·
  แถวที่โผล่มามี badge เหตุผล (neutral, `payroll_statutory_skip` ใน status_map) นำหน้า badge
  "เงินสมทบตามกฎหมาย" และ **ใส่ค่าใหม่ได้ตามปกติ** = บังคับเฉพาะรอบนี้ (recalculate เขียนทับ employee_amount
  โดยไม่สนใจ note จริง — ยืนยันจากโค้ดและจากการบันทึกจริง)
- ซ่อนจนกลุ่ม "ภาครัฐ" ว่าง → หัวกลุ่มซ่อนไปด้วย กลับมาพร้อมกันตอนกด "แสดง"
- toggle แตะแค่ class ไม่แตะค่า/สถานะ disabled ของ field ใด → dirty-guard ไม่ขยับ (ยืนยัน: ปุ่มบันทึกยัง
  disabled ทั้งก่อนและหลังกด)

## แถวที่ปิดจาก Run Settings ปรากฏคงที่ทั้งก่อน/หลังคำนวณ

`syncDeductionLinesForEmployee()`'s fallback เดิมเก็บเฉพาะ code ที่มี override ส่วนตัว — item ที่ **รอบ**
ปิดไว้จึงโผล่เฉพาะตอนที่ breakdown ยังมีมันอยู่ แล้วหายไปหลัง recalculate ครั้งถัดไป (การตั้งค่าเดียวกัน
แต่เห็นตาราง 2 แบบ) · ตอนนี้ fallback รวม `payroll_run_item_exclusions` ของรอบด้วยเสมอ (+14 บรรทัด)
ยืนยันจริง: item `OT` ที่รอบปิดไว้และพนักงานไม่มีบรรทัดคำนวณ ปรากฏเป็นแถว disabled **ทั้งก่อนและหลัง**
`recalculate()` และไม่ซ้ำแม้จะถูกปิดทั้ง 2 ระดับพร้อมกัน

## คอลัมน์ "ประวัติ" — ย้อนค่าเก่าได้จากในตาราง

`payroll_run_line_override_history` มีข้อมูลครบอยู่แล้ว (action/old/new/note/ผู้แก้/เวลา, append-only
เขียนจาก `lineOverrideSave()` และ `lineOverrideRemove()` เอง) และ `lineOverrideAuditDiff()` ก็มี filter
รายพนักงานอยู่แล้ว — ที่ขาดคือ **endpoint อ่าน** เท่านั้น จึงเพิ่ม read-only 1 ตัว
`GET api/payroll-run.line-override-history?run_id&employee_id`

**ทำไมไม่ใช้ `employee-adjustments` เดิม**: endpoint นั้นตั้งต้นจากแถวใน `payroll_run_line_overrides`
→ บรรทัดที่ override ถูกลบไปแล้วจะหายจากผลลัพธ์ ทั้งที่ประวัติยังอยู่ — ซึ่งเป็นเคสหลักของการ "ย้อนกลับ"
พอดี · masking ใช้ **ฟังก์ชันเดียวกัน** กับ endpoint พี่น้อง (`maskOverrideDiffLine()` แยกออกมาจาก
`maskEmployeeAdjustments()` ไม่ก็อปปี้) เพราะทั้งคู่ส่งตัวเลขเงินเดือนชุดเดียวกัน — ทดสอบล็อกว่าเป็น `XXXX`
ครบทุก field (original/current/ทุก edit) และ **null ยังเป็น null** (ไม่แปลงเป็นตัวเลขปลอม) ส่วน
action/เวลา/ชื่อผู้แก้ ต้องรอดมาเสมอ (ไม่ใช่ข้อมูลเงินเดือน)

- badge `แก้ไข N` (neutral ▾, `badgeDropdownHtml` โหมด action menu) ขึ้นเฉพาะแถวที่มีประวัติจริง
- dropdown: แถวแรกเสมอ "ค่าที่ระบบคำนวณ · X" (ถ้า `original_value` เป็น null = ไม่มีตัวเลข แต่ยังเลือกได้
  เพราะความหมายคือ "เอา override ออก") แล้วรายการ "ค่า · วันที่ เวลา · ชื่อผู้แก้" ใหม่→เก่า · ค่าปัจจุบัน
  มี badge "ปัจจุบัน" และ `disabled` (เลือกแล้วเป็น no-op ที่ทำให้แถว dirty เปล่าๆ) · `history_available`
  เป็น false → footnote 1 บรรทัดท้ายเมนู "ประวัติเริ่มเก็บตั้งแต่ …"
- เลือกแล้ว **ไม่ยิง API** — แค่เติมช่อง "ค่าใหม่" + ทำเครื่องหมาย `data-from-history` + ไฮไลต์ช่อง
  (พิมพ์ทับเองทีหลัง = ล้าง flag เพราะไม่ใช่การย้อนค่าที่เคยบันทึกไว้แล้ว) · ตอนกดบันทึก ถ้ามีแถวแบบนี้
  `showConfirm` tone warning บอกจำนวนก่อนยิง
- โหลดประวัติ **พร้อม request ของตาราง 1 ครั้งตอนเปิด modal** (ไม่ lazy): ต้องรู้ตั้งแต่ตอน render ว่า
  แถวไหนมีประวัติถึงจะวาด badge ได้

## footer: slot ซ้าย + "ยกเลิกการแก้ไข"

ปุ่ม "คืนค่า" เดิมสับสน 2 ทาง — ชื่อชนกับ "คืนค่าที่ระบบคำนวณ" (ซึ่งตอนนี้คือการล้างช่องให้ว่าง) และ
**ไม่เคยถูก disable** จึงกดได้ตลอดแม้ยังไม่ได้แก้อะไร (กดแล้วไม่มีอะไรเกิดขึ้น = ดูเหมือนปุ่มเสีย)
→ เปลี่ยนเป็น **"ยกเลิกการแก้ไข"** วางใน **slot ซ้ายของ footer** (`modalFooterButtonsHtml({left, leftHtml})`
ใหม่ + rules.md §9) `disabled` จนกว่า tab จะ dirty จริง · แถวซ่อนย้ายจากบรรทัดใต้ตารางมาเป็น `<tr>`
สุดท้ายของตาราง (สิ่งที่มันเปิดคือ "แถว" จึงควรอยู่ในกริดเดียวกัน)

## บั๊กของตัวเองที่เจอตอนทดสอบเบราว์เซอร์ (แก้แล้วในรอบเดียวกัน)

กดบันทึกหลังแก้ 2 แถว แต่ progress ขึ้น "กำลังบันทึก 2/**3**…" — แถวที่สามคือแถวที่ **ถูกปิดไว้ที่ Run Settings**
(checkbox disabled + ไม่ได้ติ๊ก) ซึ่ง `lineOverrideRowPlanRd()` อ่านว่า "ผู้ใช้ติ๊กออก" แล้วส่ง
`action='exclude'` **ส่วนตัว** ให้พนักงานคนนั้นทั้งที่ไม่มีใครแตะ (ผลข้างเคียงจริง: override ส่วนตัวชนะระดับรอบ
เสมอ แถวนั้นจะยกเลิกไม่ได้จาก Run Settings อีกต่อไป) — แก้โดยให้ฟังก์ชันคืน `null` ทันทีเมื่อ checkbox ของแถว
`:disabled` (แถวที่ระบบปิดไว้ไม่มีเจตนาของผู้ใช้อยู่ในนั้นเลย) ยืนยันหลังแก้: แก้ 2 แถว = ยิง **2/2**

## รอบ 4 (2026-09-16): dropdown ประวัติ 3 ส่วน + modal ซ้อน + "คืนค่าระบบทั้งหมด"

### dropdown: ทำไมเป็นหัว/list/ท้าย ไม่ใช่ "5 แถวล่าสุด + ดูทั้งหมด"
แบบแรกที่ทำไป (ตัดเหลือ 5 แถวแล้วต่อท้ายด้วย "ดูประวัติทั้งหมด (N)…" เมื่อ N > 5) ถูกสั่งเปลี่ยนทั้งข้อ
เหตุผลที่ยกมาใช้ต่อได้: **เมนู 5 แถวหน้าตาเหมือนกันเป๊ะ** ไม่ว่าเส้นนั้นจะมีการแก้ 5 ครั้งหรือ 40 ครั้ง —
ผู้ใช้ไม่มีทางรู้จากหน้าจอว่าอะไรหายไป ถ้าเงื่อนไข `> 5` พังเมื่อไหร่ก็เงียบสนิท · ของใหม่จึงแสดง **ครบทุกแถว**
แล้วให้ตัวเมนูเองเป็น scroll container สูงประมาณ 5 แถว, หัว/ท้ายเป็น `position: sticky` ของตัวเอง
(`--lo-history-row-h`, วัดจริง 34px/แถว) — `padding: 0` ที่เมนูจำเป็น เพราะ padding ของ scroll container
จะโผล่เหนือหัว sticky เป็นแถบพื้นหลัง

**หัว = ค่าที่ระบบคำนวณ และ "ไม่ใช่ตัวเลือก"** — ทุกแถวข้างล่างคือส่วนต่างจากมัน มันจึงเป็นบริบทไม่ใช่
ของให้เลือก (เดิมเป็น `dropdown-item` เลือกได้ = "ลบ override") · การกลับไปใช้ค่าระบบตอนนี้มี 3 ทางที่ชัดกว่า:
ล้างช่องค่าใหม่ให้ว่าง, ปุ่ม "คืนค่าระบบทั้งหมด", หรือปุ่ม "ใช้ค่านี้" บนแถวบนสุดของ modal

**ท้าย = ทางเดียวที่เข้า modal** และแสดงเสมอเมื่อมีประวัติอย่างน้อย 1 ครั้ง (badge เองก็ขึ้นเมื่อ ≥ 1 อยู่แล้ว)
— ไม่มีเงื่อนไขจำนวนซ่อนอยู่ให้พังเงียบ

**แถวที่เป็นค่าปัจจุบัน**: badge neutral "ปัจจุบัน" **นำหน้า** meta เดิม ไม่ใช่แทนที่ — "อันไหนคือค่าที่ใช้อยู่"
เป็นข้อมูลเพิ่ม ไม่ใช่เหตุผลให้ทิ้งเวลา·ผู้แก้ของแถวนั้น · และหา "แถวไหนคือปัจจุบัน" ด้วย
`lineOverrideHistoryCurrentIndexRd()` = ตัว**ใหม่สุด**ที่ค่าตรงกับค่าที่ใช้อยู่ ไม่ใช่ทุกแถวที่ค่าเท่ากัน
(ค่าเดิมถูกตั้ง → เปลี่ยน → ตั้งกลับ เกิดขึ้นได้จริง) — ทั้ง dropdown และ modal ใช้ตัวเดียวกัน

### modal ซ้อน: ไม่ต้องเขียน z-index/scroll-lock ใหม่เลย
`app.js` มี handler กลางอยู่แล้วทั้ง 2 เรื่อง (bump z-index ของ modal ที่ไม่ใช่ตัวแรก + คืน `modal-open`
ให้ body เมื่อยังมี modal อื่นเปิดค้าง) — วัดจริง: main 1055 / nested 1085, backdrop 1050 / 1075,
ปิดแล้ว body ยังมี `modal-open`, modal หลักยัง `show` และ scroll ไม่กระโดด

รายการใน modal ใช้ `renderTimeline()` เดิม + ช่อง `item.actionHtml` ที่เพิ่มใหม่ (ดู rules.md §6) —
แถว "ค่าที่ระบบคำนวณ" ไม่มีวันที่ของตัวเอง จึง pin ไว้บนสุดด้วย `time: ''` แล้วซ่อนหัววันที่ว่างด้วย
`.timeline-day-header:empty` (เปิด `groupByDay` ไว้เพราะหัวรายการของ timeline พิมพ์แค่ HH:mm —
ไม่มีหัววัน การแก้คนละวันจะอ่านเป็นเวลาเดียวกัน)

### "คืนค่าระบบทั้งหมด" = mark ไม่ใช่ยิง
ปุ่มนี้ **ไม่เรียก endpoint ใดๆ เอง** — มันติด `data-force-remove="1"` ให้ทุกแถวที่มี override จริง
(ข้ามแถวที่ Run Settings ปิด) เติมค่าที่ระบบคำนวณลงช่องเพื่อให้เห็นว่าจะได้อะไร แล้วปล่อยให้ปุ่มบันทึกเดิม
ทำงานตามปกติ · `lineOverrideRowPlanRd()` อ่าน mark **ก่อน**อ่านช่องค่าเสมอ เพราะแถวที่ mark ไว้
"หมายถึง" การลบ override (`.remove`) — ถ้าอ่านช่องกลับไปจะกลายเป็นการ**บันทึกค่าที่ระบบคำนวณเป็น override
ตัวใหม่** ซึ่งตรงข้ามกับชื่อปุ่ม · ค่าที่ระบบคำนวณรู้ได้จากประวัติเท่านั้น (เป็นค่าที่การแก้ครั้งแรกไปทับ)
ถ้าไม่มีประวัติช่องจะว่าง — แถวยัง mark อยู่ และ `showConfirm` ตอนบันทึกคือสิ่งที่บอกจำนวนที่กระทบ
· เพราะ mark อาจไม่เปลี่ยนค่าใน field เลย `adjustmentTabIsDirty()` จึงนับ `[data-force-remove="1"]`
เป็น dirty ตรงๆ ไม่ผ่าน `isFormDirty()` อย่างเดียว

## รอบที่ 5: ช่อง "ค่าใหม่" = สิ่งที่จะเปลี่ยนเท่านั้น (บั๊กข้อมูลหาย)

**อาการที่ user ทำซ้ำได้**: แถวที่มี override 40,000 อยู่ — ติ๊กออกแล้วติ๊กกลับ (ช่องถูกล้างตอนติ๊กออก)
แล้วกดบันทึก → **override ถูกลบ** โดยที่หน้าจอไม่เคยบอกว่ากำลังจะลบ

**สาเหตุ**: ช่องนี้เคย **prefill** ค่า override เดิมลงไป ทำให้ "ว่าง" ต้องแปลว่า "กลับไปใช้ค่าที่ระบบคำนวณ"
(`.remove`) — พอมีอะไรก็ตามที่ล้างช่องนั้น (การติ๊กออก, กดลบเอง) ความหมายของแถวก็กลายเป็น "ลบ override" ทันที
โดยไม่มีอะไรบนหน้าจอบอก · เหตุผลเดิมที่ prefill คือ "ไม่อยากให้แถวที่มี override ดูเหมือนแถวว่าง" — แต่
**คอลัมน์ "ค่าปัจจุบัน" ข้างๆ ก็แสดงค่าที่ใช้อยู่จริงอยู่แล้ว** prefill จึงไม่ได้บอกอะไรเพิ่มเลย แลกมาด้วยการทำให้
"ว่าง" มีสองความหมาย

**หลักการใหม่**: ช่อง "ค่าใหม่" คือ**สิ่งที่จะเปลี่ยนเท่านั้น** — เริ่มว่างเสมอ และ **ว่าง = ไม่แตะ**
เสมอ ทุกแถว · การกลับไปค่าที่ระบบคำนวณต้อง**พูดออกมาตรงๆ** — แถวบนสุดของเมนูประวัติ หรือปุ่ม
"คืนค่าระบบทั้งหมด" ซึ่งทั้งคู่ mark แถว (`data-force-remove`) ไม่ได้อาศัยความว่างของช่อง

### ตารางความจริง (`lineOverrideRowPlanRd()`, เรียงตามลำดับที่โค้ดเช็ค — ตัวแรกที่ตรงชนะ)

| # | สภาพแถว | สิ่งที่ยิง |
|---|---|---|
| 1 | mark จากประวัติแถว "ค่าที่ระบบคำนวณ" หรือปุ่ม "คืนค่าระบบทั้งหมด" (`data-force-remove`) | `.remove` (ถ้าแถวนั้นมี override อยู่จริง) |
| 2 | ปิดจาก Run Settings (checkbox `disabled`) | ไม่ยิง — แถวนี้ไม่มีเจตนาของผู้ใช้อยู่เลย |
| 3 | ☐ (ติ๊กออก) | `exclude` (ถ้าเดิมไม่ได้ exclude อยู่แล้ว) |
| 4 | ☑ + ว่าง บนแถวที่เดิมเป็น `exclude` | `.remove` — คือการยกเลิก exclude นั้น |
| 5 | ☑ + มีค่า | `override_amount` (รวมกรณีที่เดิมเป็น `exclude` — 1 request เดียวทับแถวเดิมให้เอง) |
| 6 | ☑ + ว่าง (กรณีอื่นทั้งหมด) | **ไม่ยิงอะไรเลย** — ข้อที่เคยผิดจนทำข้อมูลหาย |

ลำดับสำคัญ: (1) อ่าน mark **ก่อน** อ่านช่องเสมอ — แถวที่ mark ไว้มีตัวเลขที่ระบบคำนวณแสดงอยู่ในช่อง
เพื่อให้เห็นว่าจะได้อะไร ถ้าอ่านช่องก่อนจะกลายเป็นการ**บันทึกค่านั้นเป็น override ตัวใหม่** ซึ่งตรงข้ามกันกับชื่อปุ่ม

### ติ๊กออกแล้วค่าที่พิมพ์ไว้ไม่หาย

ติ๊กออก → พักค่าที่พิมพ์ไว้ที่ `data-typed-amount` แล้วล้างช่อง; ติ๊กกลับ → คืนค่านั้น — การติ๊กกลับ
คือการ undo และ undo ที่ทำตัวเลขที่เพิ่งพิมพ์หายก็ไม่ใช่ undo

### dirty

เทียบกับ**สภาพตอนโหลด** ตามเดิม (`isFormDirty()` + baseline ที่ snapshot ตอนโหลดเสร็จ) — พอช่องเริ่มว่างทุกแถว
"☑ + ว่าง ที่ไม่เคยแก้" จึงไม่ dirty โดยอัตโนมัติ ไม่ต้องเขียนกฎพิเศษ (ส่วน mark `data-force-remove` นับเป็น dirty ต่างหาก
เพราะมันอาจไม่เปลี่ยนค่าใน field เลย — ดู `adjustmentTabIsDirty()`)

## รอบที่ 6: เลิก stage ทั้งหมด — แก้ทีละรายการ ยิงทันที

tab นี้เริ่มต้นเป็น **ฟอร์มที่ stage ไว้แล้วกดบันทึกทีเดียว** แต่ backend ไม่เคยมี endpoint แบบ batch —
ปุ่มบันทึกเดียวนั้นยิงทีละแถวเรียงกันอยู่ดี (`docs/specs/line-override-batch.md` เขียนสเปกไว้แต่ไม่เคยทำ)
สิ่งที่ "รวมเป็นชุด" จริงๆ จึงมีแค่**ความเสี่ยง**: ผู้ใช้เห็นสภาพที่ยังไม่มีอยู่จริงบนเซิร์ฟเวอร์ และทุกกฎที่
ตามมาก็เกิดขึ้นเพื่ออธิบายสภาพชั่วคราวนั้นล้วนๆ —

- "ว่าง = อะไร" (รอบที่ 5 ทั้งรอบ เกิดจากข้อนี้ข้อเดียว และทำข้อมูลหายจริง)
- ติ๊กออกต้องพักค่าที่พิมพ์ไว้ แล้วติ๊กกลับต้องคืน
- mark `data-force-remove` / `data-from-history` เพื่อบอกว่าแถวนี้ "หมายถึง" อะไรตอนกดบันทึก
- dirty-guard ที่ต้องรู้ว่า mark นับเป็น dirty ด้วย ทั้งที่ไม่มี field ไหนเปลี่ยน

**ตัดสินใจ: ยิงทันทีทีละรายการ** เหมือน tab "รายการจ่าย" ที่อยู่ข้างกัน — เข้ากฎเดียวกัน
(*tab ที่ยิง API ทันที ซ่อนปุ่มบันทึกของ footer*, rules.md §9) · กฎ 4 ข้อข้างบนหายไปทั้งหมดพร้อมกับ
`lineOverrideRowPlanRd()` เพราะไม่มีสภาพชั่วคราวให้ต้องอธิบายอีกต่อไป — สิ่งที่อยู่บนหน้าจอคือสิ่งที่
อยู่บนเซิร์ฟเวอร์ เสมอ

`docs/specs/line-override-batch.md` **ยังเก็บไว้** (เผื่อวันหนึ่งมี endpoint จริง) แต่**ไม่จำเป็นแล้ว**:
ปัญหาที่มันแก้ (5 แถว = 5 recalculate) ตอนนี้กลายเป็น "1 การกระทำ = 1 recalculate" ซึ่งเป็นสิ่งที่ผู้ใช้
รอได้อยู่แล้ว เหลือแค่ปุ่ม "คืนค่าระบบทั้งหมด" ที่ยังยิงทีละแถวเรียงกัน (มี progress เหมือนเดิม)

### สิ่งที่ยิงจริง ต่อการกระทำ

| การกระทำ | ยิงอะไร |
|---|---|
| ดินสอ → แก้ตัวเลข → บันทึก / Enter | `override_amount` (ค่าเท่าเดิมหรือว่าง = ปุ่ม disabled ไม่ยิง) |
| switch ปิด → ยืนยัน | `exclude` |
| switch เปิด → ยืนยัน | `.remove` (ยกเลิก exclude) |
| ประวัติ → "ใช้ค่านี้" ที่แถวค่าเดิม → ยืนยัน | `override_amount` |
| ประวัติ → "ใช้ค่านี้" ที่แถว "ค่าที่ระบบคำนวณ" → ยืนยัน | `.remove` |
| footer → คืนค่าระบบทั้งหมด → ยืนยัน | `.remove` ทีละแถวเรียงกัน |

ทุกอย่างจบด้วย `loadSyncLineOverridesRd()` + `loadRunDetail()` — **โหลดใหม่ทั้งตาราง ไม่ patch เฉพาะแถว**
เพราะ override หนึ่งตัวเปลี่ยนผลของภาครัฐทั้งชุด (และยอดรวมของรอบ) ไม่ใช่แค่แถวที่แก้

### ระหว่างยิง ตารางถูกล็อกทั้งตาราง

แต่ละ save เรียก `recalculate()` ทั้งรอบภายใน — การกระทำที่สองที่เริ่มก่อนตัวแรกกลับมาจะแข่งกันเขียน ·
ล็อกแค่**ตาราง** ไม่ใช่ทั้ง modal (tab อื่นไม่เกี่ยว) · แถวที่กำลังบันทึกมี spinner บนปุ่มบันทึกของตัวเอง ·
**ล้มเหลว = ปลดล็อก + `showError` + ค่าที่พิมพ์ยังอยู่ในช่อง** ให้แก้แล้วลองใหม่ ไม่ใช่เริ่มใหม่

### switch ถามทั้งสองทาง

ไม่ใช่แค่ตอนปิด — การเปิดกลับก็เปลี่ยนเงินที่พนักงานได้รับเหมือนกัน · ยกเลิก = switch เด้งกลับ
(ไม่ปล่อยให้ control ขัดกับข้อมูลข้างหลัง) ไม่ยิงอะไร
