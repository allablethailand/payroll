## ตาราง line-override: 1 implementation 2 mount

ทั้ง tab "ปรับตัวเลข" และ modal นี้ใช้ **ชุดฟังก์ชันเดียวกันทั้งหมด** (render/switch/inline edit/dropdown
ประวัติ/modal ประวัติ/แถวซ่อน/busy lock) — ไม่ก๊อป ไม่ fork

สิ่งที่เคยผูกกับ `#lineOverrideTableWrap` ตรงๆ กลายเป็น 2 อย่าง:
- **handler ทุกตัว delegate บน `.lo-mount`** (class ที่ทั้ง 2 จุดมี) แทน id ของ tab 3
- **`lineOverrideHostRd`** = ความต่างทั้งหมดระหว่าง 2 host: render ที่ไหน (`mount`), ของพนักงานคนไหน
  (`employeeId`), หลังบันทึกต้องรีเฟรชอะไรเพิ่ม (`onSaved`), และเป็น tab 3 หรือไม่ (`isAdjustmentsTab`)

`isAdjustmentsTab` จำเป็นเพราะ response ก้อนเดียวกันของ `sync-lines-for-employee` ยังพ่วง radio
Tax/SSO ของ tab 5 + dirty guard + ปุ่ม footer ของ modal นั้นมาด้วย — host อื่นข้ามทั้งหมด ไม่ใช่ปล่อยให้
ยิงใส่ markup ที่ไม่ได้อยู่บนจอ (re-baseline dirty guard ของ pane ที่ไม่ได้เปิดไม่ใช่ no-op)

### id ซ้ำ: กันที่ต้นทาง ไม่ใช่หวังว่าจะไม่ชน

ตารางที่ render ออกมามี id จริงอยู่ข้างใน (`loInc{n}`, `lineOverrideHiddenRow`,
`btnToggleHiddenLineOverrides`) — tab 3 ยังอยู่ในหน้าจนกว่าจะถึงก้อนลบ และ markup ที่มันเคย render ค้างอยู่
ใน DOM หลังปิด modal ถ้า mount ที่สอง render ทับตอนนั้นก็ได้ id ซ้ำทันที

`setLineOverrideHostRd()` จึง **ล้าง mount อีกตัวเสมอเมื่อเปลี่ยน host** — วัดจริงด้วย Playwright
(สแกน `[id]` ทั้ง document ด้วย `getAttribute('id')` ไม่ใช่ `el.id`; `el.id` บน `<form>` ที่มี control
ชื่อ `id` จะคืน Node ไม่ใช่ string): เปิด modal → เปิด Adjustments tab 3 (4 แถว) → ปิด → เปิด modal ใหม่
(4 แถว, tab 3 เหลือ 0) → **ไม่มี id ซ้ำเลยสักตัวในทุกสถานะที่วัด**

## "รายการที่เพิ่มเอง" และแถบยอดสุทธิ: ขยาย component ไม่ใช่ก๊อป grid

`payslipViewHtml()` ได้ช่อง optional เพิ่ม 2 ตัว + แยกแถบสุทธิออกมา 1 ฟังก์ชัน — ทั้งหมด backward
compatible (caller เดิมที่ไม่ส่งอะไรได้ผลเท่าเดิมทุกตัวอักษร ล็อกด้วย test):

| เพิ่มอะไร | ทำไมไม่ก๊อป markup ไปไว้ที่ caller |
|---|---|
| `earningTitleActionHtml` / `deductionTitleActionHtml` | ปุ่ม + บนหัวคอลัมน์ — grid 2 คอลัมน์ของสลิปคือสิ่งที่ component นี้มีไว้ป้องกันไม่ให้มีสำเนาที่สอง (§0.4) |
| `showTotals: false` | หน้านี้ไม่มียอดรวมต่อคอลัมน์ ยอดเดียวที่มีความหมายคือยอดสุทธิของรอบ ซึ่งอยู่ในส่วน (3) |
| `payslipNetSummaryHtml()` | ส่วน (3) ต้องเป็น**แถบเดียวกัน**กับที่สลิปจบด้วย — สำเนาที่สองคือจุดที่ "ยอดจ่ายสุทธิ" 2 ที่เริ่มหน้าตาไม่เหมือนกัน |

`showTotals: false` ยัง**ปิดแถว "-" placeholder ของคอลัมน์รายการหักด้วย**: "-" มีไว้กันไม่ให้คอลัมน์เป็น
ช่องว่างระหว่างหัวกับแถบยอดรวม พอไม่มีแถบยอดรวมก็ไม่มีอะไรให้มันค้ำ และคอลัมน์ "เงินได้" ไม่เคยมี "-"
อยู่แล้ว — ปล่อยไว้จะกลายเป็นสิ่งเดียวบนจอที่ 2 ฝั่งไม่เหมือนกัน (เจอจริงจากภาพ)

แถวของรายการที่เพิ่มเองใช้ `manualLineListItemHtml()` ตัวเดิมของ Adjustments modal ทั้งดุ้น
(ยังไม่มีปุ่มแก้/ลบในก้อนนี้) · ปุ่ม + เป็น `.btn-icon` (§7) 32px **disabled + tooltip** ในก้อนนี้ —
render ไว้ให้หัวคอลัมน์หน้าตาเหมือนตอนใช้งานได้จริง ไม่ใช่โผล่มาทีหลัง

## หลัง save ต้องรีเฟรชยอด (3) จาก server ไม่ใช่คำนวณเอง

override ตัวเดียวเปลี่ยนผลของภาครัฐทั้งชุด → ยอดสุทธิของรอบเปลี่ยนตาม · `onSaved` hook ของ host นี้จึง
ยิง `api/payroll-run.get` แล้วอ่านแถวของพนักงานคนนี้กลับมาใหม่ ไม่บวกลบเองฝั่ง client
· ยืนยันจริงในเบราว์เซอร์: แก้ฐานเงินเดือนจาก 30,000 → 28,500 แล้วยอดสุทธิขยับ 30,456.67 → 29,031.67
และตารางถูกล็อก (`lo-table-busy`) ระหว่างยิงจริง

## ตาราง "จากระบบ" ไม่รวมบรรทัดที่คนเพิ่มเอง

บรรทัดที่คนเพิ่มเอง (`source: 'manual_line'`) **ไม่มี switch/ดินสอในตารางนี้** — มันมีที่ของมันเองอยู่แล้ว
(tab "รายการจ่าย" ที่แก้/ลบได้ในฐานะแถวจริงของมัน) · เหตุผลที่หนักกว่าความซ้ำ: **override key ด้วย item_code
แต่ manual line 2 แถวใช้ item_code เดียวกันได้** (คอมเมนต์ใน `recalculate()` ระบุไว้เอง) — override บน code
นั้นจึงไม่มีทางหมายถึงแถวใดแถวหนึ่งได้แม้ในหลักการ

**กรองที่ `syncDeductionLinesForEmployee()` จุดเดียว ไม่ส่ง field `source` ออกมาให้ client กรองเอง**
(endpoint เดิมไม่มีทั้ง `source` และ `manual_line_id` — ยืนยันจากการเรียกจริง ไม่ใช่จากการอ่านโค้ด) —
ทุก caller จึงตรงกันโดยไม่มีใครต้องจำว่าต้องกรอง รวมทั้ง mount ทั้งสองของตารางและ caller ใหม่ในอนาคต ·
ราคาที่จ่ายคือ client ไม่มีทางรู้เลยว่ามีแถวถูกกรองออกไป (รับได้: หน้านี้แสดงแถวเหล่านั้นอยู่แล้วใน block
"รายการที่เพิ่มเอง" ข้างล่าง)

แถวที่ถูกกรอง**ไม่ได้ถูกเอาออกจาก payroll** — ยังอยู่ใน breakdown ที่สลิป render และอยู่ในยอดที่พนักงาน
ได้รับจริง (test ล็อกทั้ง 2 ข้อ) — กรองออกจาก endpoint เดียว ไม่ใช่การตัดออกจากการคำนวณ

`$seenCodes` **ไม่ถูกตั้งให้แถวที่กรองทิ้ง** โดยตั้งใจ: set นั้นมีไว้กัน fallback loop ข้างล่าง list ซ้ำ
สิ่งที่ loop นี้ปล่อยออกไปแล้ว ซึ่งแถวนี้ไม่เคยถูกปล่อย · fallback list เฉพาะ code ที่มี override
`action='exclude'` ซึ่งตามนิยามไม่อยู่ใน breakdown อยู่แล้ว ทั้งสองจึงชนกันไม่ได้

**ตัวเลข dev DB ตอนกรอง (ไม่ได้ลบอะไร)**: breakdown line ทั้งหมด 11 แถว · `source=manual_line` 2 แถว ·
**override ค้างบน code ที่เป็น manual_line = 0 แถว** · **history ค้าง = 0 แถว** (ทั้ง DB มี
`payroll_run_line_overrides` 0 แถว) — การกรองจึงไม่ทำให้ override ของใครเข้าไม่ถึงใน dev ·
**บน production ไม่ได้ตรวจ** — ถ้ามีแถวอยู่จริง override นั้นจะยังมีผลกับการคำนวณต่อไป (recalculate
ไม่ได้เปลี่ยน) แต่จะมองไม่เห็น/กดยกเลิกจากหน้านี้ไม่ได้ — flag ไว้ตรงๆ ถ้าเจอจริงต้องมีทางเก็บกวาดต่างหาก

## รายการที่เพิ่มเอง: ไม่พิมพ์ item_code

`manualLineListItemHtml()` เคยพิมพ์ `item_code` ของ catalog line (BONUS/UNIFORM_DEDUCT) ไว้ข้างชื่อ —
เป็นรหัสภายใน ไม่ใช่สิ่งที่ผู้ใช้อ่านแล้วได้ความหมายเพิ่ม ในเมื่อชื่อบอกอยู่แล้วว่าคืออะไร · ย้ายไปเป็น
`title` ของชื่อแทน (tooltip) ตามที่ `breakdownLineRowsRd()` ทำกับ code ของมันไปแล้วรอบก่อน

**badge custom/other ยังอยู่** — มันไม่ใช่รหัส แต่เป็นการจำแนกตัวบรรทัดเอง (คนพิมพ์เข้ามาเอง / เป็นปลายทาง
"อื่นๆ") ซึ่งเป็นเส้นแบ่งเดียวกับที่ `breakdownLineRowsRd()` ใช้อยู่แล้ว · แก้ที่ฟังก์ชันเดียว →
tab "รายการจ่าย" เปลี่ยนตามด้วย (ตั้งใจ) · `.manual-line-code` ใน style.css ถูกลบทิ้งพร้อมกัน ไม่เหลือ dead CSS

## ความสูง modal: ตามเนื้อหา ไม่ตรึง

เคยใส่ `.modal-tabbed` (`docs/decisions/2026-09-15-modal-tabbed-height.md`) เฉพาะ branch ที่แก้ได้
เพื่อกัน modal ขยับความสูงทุกครั้งที่ตาราง render ใหม่หลังบันทึก — **ถอดออกแล้ว**: modal นี้ไม่มี tab
สิ่งที่ได้มาคือความนิ่งข้าม save แลกกับราคาที่เอกสารนั้นเองระบุไว้สำหรับเนื้อหาสั้น (วัดจริง: เหลือช่องว่าง
ท้าย modal ~140px) · ตอนนี้ทั้ง 2 สถานะสูงตามเนื้อหา และเลิก `modal-fullscreen-sm-down` ที่เคยพ่วงมาคู่กันไปด้วย
(กฎ `< sm` ของ `.modal-tabbed` ปลด `max-height` โดยถือว่า dialog เต็มจออยู่แล้ว — พอไม่มี `.modal-tabbed`
ก็ไม่ต้องมีมัน) · ที่ 430 body เลยจอไปก็ scroll ในตัวเองตาม `modal-dialog-scrollable` เดิม

## บั๊กจริงที่เจอและแก้: `display:flex` บน `<td>` ฆ่า colspan

(จากโครงรุ่นแรกของรอบเดียวกัน ที่หัวกลุ่มเป็นแถวในตาราง) — ตั้ง `display:flex` บน `<td>` ตรงๆ ทำให้เซลล์
เลิกเป็น table-cell ทั้งใบ `colspan` หายไปด้วย ความกว้างยุบเหลือเท่าคอลัมน์ตัวเลข (38% ของ
`table-layout: fixed`) วัดจริง: ปุ่มลอยห่างขอบขวา **298.59px**, label ตัด **3 บรรทัด**, หัวสูง 69px →
ครอบ `<div>` ข้างในแล้ว flex ที่ div: ปุ่มไปอยู่ที่ 12px, label 1 บรรทัด 18px, หัวสูง 32px — ขึ้นเป็นกฎใน
rules.md §7 เพราะเป็นกับดักของ `<td>` ทุกตัว ไม่ใช่ของหน้านี้

## พิจารณาแล้วไม่ใช้: `override_action`/`history_count` ใน `payroll-run.get`

โครงรุ่นแรกเพิ่ม 2 field นี้ต่อบรรทัด breakdown (prefetch 2 query ต่อ request จาก
`payroll_run_line_overrides` + `payroll_run_line_override_history` แล้ว merge ใน PHP ด้วย
employee_id+item_code) เพื่อให้แถวในสลิปรู้สถานะ override ของตัวเองตั้งแต่ตอน render

**ถอดออกทั้งหมด** เมื่อโครงเปลี่ยนมาใช้ตาราง line-override ตัวจริง: ตารางนั้นโหลดข้อมูลของตัวเองจาก
`sync-lines-for-employee` + `line-override-history` อยู่แล้ว ซึ่งมีครบกว่า (`override_amount`, note,
occurrences, ประวัติเต็มรายการ ไม่ใช่แค่จำนวนครั้ง) — 2 field ใหม่จึงเป็นข้อมูลชุดที่สองที่ไม่มีใครอ่าน
และเป็น 2 query ต่อการเปิดหน้า Payroll Detail ทุกครั้งโดยเปล่าประโยชน์ · `PayrollRunModel::getDetails()`
กลับไปเท่าเดิมทุกบรรทัด, `tests/breakdown_line_override_meta_test.php` ถูกลบพร้อมกัน

ถ้าวันหนึ่งต้องการ badge สถานะ override บน**สลิปโหมดอ่าน** (ที่ไม่มีตาราง) ให้กลับมาอ่านหัวข้อนี้ก่อน —
วิธีที่ใช้ได้จริงคือ prefetch แบบเดิม แต่ต้องมี consumer จริงก่อน
