## Setup & Rules (`Time & Leave` menu → 5 แท็บ: Shift/Holiday/Leave Type/OT Rate/Work Location)
- Backend เต็มรูปแบบใน `SetupRulesModel`/`SetupRulesController` ครบทั้ง 5 แท็บ
- **OT Rate** (`ot_rates` + `master_ot_scope_types`): "Applies To" (เดิม hardcode Weekday/Weekend/Holiday ใน mockup) ย้ายเป็น master table ตาม convention เดียวกับ leave category/payslip field — seed ไว้ 3 ค่า `calculation_base` ยังเป็น enum('hourly','daily') ธรรมดา ไม่ทำ master table เพราะเป็นตัวเลือกที่ผูกกับสูตรคำนวณจริง ไม่ใช่ list ที่ธุรกิจจะเพิ่มเองได้ตามใจ — **ไม่ผูก scope กับ employee/shift แบบ Holiday** (ไม่มี requirement เพิ่มเติมแบบ Holiday/Leave Type ตอนสั่งงาน จึงทำแค่ระดับ company-wide config ธรรมดา) **ยังไม่ได้ enforce ขั้นต่ำตามกฎหมายแรงงาน** (เช่น 1.5x ขั้นต่ำวันธรรมดา) เพราะไม่มั่นใจตัวเลขที่ verify แล้ว เป็นแค่ config tool ให้ตั้งเอง ไม่ใช่ compliance validator — ทดสอบด้วย `tests/ot_rate_test.php` (13 assertions)
- **`shifts` และ `master_work_locations` ถูกสร้างขึ้นเพื่อเป็น dependency ของ Holiday scope (shift) และของ `employees.work_location_id`** ซึ่งเดิมเป็นคอลัมน์ที่มีอยู่ในสคีมาแต่ไม่เคยมี master table รองรับมาก่อน (เหมือนกรณี `external_reference_no` ที่ wire ตอนทำ `StudentLoanReport`) — `employees.shift_id`/`work_location_id` ตอนนี้มี FK จริงแล้ว (`ON DELETE SET NULL ON UPDATE CASCADE`) และ dropdown ในหน้า Employee Detail ต่อ `data-api`/`select2-remote` แล้ว (เดิมเป็น native `<select>` ที่ไม่มี option ให้เลือกเลย)
- **Holiday** (`holidays` + `holiday_assignments`): assign หลายแบบพร้อมกันต่อ 1 รายการ (shift/department/position/employee) ผ่าน `assignment_mode` ('include'=whitelist / 'exclude'=blacklist ทุกคนยกเว้นที่เลือก) — mode='include' ต้องมีอย่างน้อย 1 scope, mode='exclude' ปล่อยว่างได้ (แปลว่าใช้ทั้งบริษัท) `holiday_assignments` ทั้งชุดถูก delete+reinsert ทุกครั้งที่ save (pattern เดียวกับ `approval_workflow_steps`) `scope_id` เป็น polymorphic เช็คที่ application layer ผ่าน `validateScopeRef()`
  - **Priority เมื่อ 2 holiday ที่ active ชนวันเดียวกันแต่ได้ผลลัพธ์ต่างกันสำหรับพนักงานคนเดียว: employee > position > department > shift** ทำใน `SetupRulesModel::resolveHolidaysForEmployee()` — **ยังไม่มี consumer จริง** (ไม่มีโมดูล attendance/payroll ไหนเรียกใช้ตอนนี้) แต่ build+test ไว้พร้อมแล้ว (`tests/holiday_test.php`) เหมือน pattern `ApprovalRequestModel` ตอนยังไม่ผูกกับ flow จริง
  - Date-collision check ตอน save เป็นแบบ **scope-blind** (เช็คแค่วันที่ชนกันไหม ไม่เช็คว่า scope จริงๆ overlap กันหรือเปล่า) เป็นการลดความซับซ้อนที่ตั้งใจ — full scope-aware overlap ให้ resolver ข้างบนจัดการตอน read แทน
  - `country_code` ของ holiday **ไม่ใช่ field ที่ผู้ใช้กรอกเอง** ระบบดึงจาก `companies.registered_country` อัตโนมัติตอน save เสมอ
- **Leave Type** (`leave_types` + `master_leave_categories` + `master_statutory_leave_minimums`): category เป็น master table (seed 10 ค่า: sick/personal/annual/maternity/ordination/military/leave_without_pay/family_parental/emergency/other) ตามด้วย field set สไตล์ HR SaaS มาตรฐาน — quota_type/amount/unit_type, requires_document, is_continuous (นับรวมวันหยุดในช่วงลาไหม), is_paid, allow_carry_over, gender_restriction, min_service_days, advance_notice_days, max_consecutive_days, applicable_employment_statuses (CSV ของ `employees.employment_status` ที่มีสิทธิ์ เช่น "permanent,contract" — ไม่ใช่ master table เพราะ enum นี้ fix อยู่แล้วในสคีมา ไม่ใช่ list ที่ต้องเพิ่มทีหลัง)
  - **`master_statutory_leave_minimums` เป็น global reference table (ไม่ผูกบริษัท)** ใช้แค่ validate ว่า `quota_amount` ของบริษัทต่ำกว่าขั้นต่ำตามกฎหมายของประเทศนั้นไหม — เช็คเฉพาะตอน `unit_type='day'` เท่านั้น (unit เป็นชม./ครึ่งวันข้ามไปเพราะเทียบกับเลขวันตรงๆไม่ได้) **ค่าที่ seed ไว้ตอนนี้มีแค่ TH annual(6 วัน)/maternity(98 วัน) และเป็น DRAFT ที่ยังไม่ verify กับตัวบทกฎหมายจริง** SG/MY ตั้งใจไม่ seed เพราะเป็น sliding scale ตามอายุงาน ใส่เลขเดียวจะผิดหลักกฎหมาย, US ไม่มี federal minimum เลยไม่ seed
- **Shift ↔ Employee assignment**: ปุ่ม "Assign Employees" ต่อแถวใน Shift tab เปิด modal multi-select พนักงาน แล้ว `SetupRulesModel::shiftAssignEmployees()` เคลียร์ `employees.shift_id` ของทุกคนที่เคยอยู่กะนี้ก่อน แล้วค่อยตั้งใหม่ให้เฉพาะคนที่เลือก (replace ทั้งชุด ไม่ diff เพิ่ม/ลบทีละคน) ownTransaction pattern ตามปกติ
- **DataTable ทุกตารางในหน้านี้ (Shift/Holiday/Leave Type/Work Location) ใช้ default `dom` ของ DataTables (native search box) + inject ปุ่ม Add เข้า `.dt-search` ผ่าน `initComplete`** — ของเดิม (ตอน mockup) มี custom `.panel-toolbar`/`.search-box` แยกอยู่เหนือตาราง ซึ่งผิด convention (เจอและแก้ตอนทำ phase 3 หลัง user สังเกตว่าไม่ตรงกับโมดูลอื่น)
- ทดสอบด้วย `tests/holiday_test.php` (24 assertions, เน้น priority engine) และ `tests/setup_rules_phase3_test.php` (24 assertions: Work Location CRUD, shift assignment replace-semantics, leave type CRUD + statutory-minimum validation)
- **RBAC** (`permissions`/`role_permissions`, ผูกกับ `structure_roles`/`employees.role_id` เดิม ไม่มี role/user_roles table ใหม่) — schema+seed (8 permissions) มาจาก phase 1, engine (`PermissionModel`) + matrix UI + enforcement ทำเพิ่มในรอบถัดมา ตาม scope ที่ตกลงไว้ (Holiday, Leave Type, Approval Workflow เท่านั้น — ไม่รวม Shift/Work Location)
  - **`PermissionModel::checkPermission($employeeId, $permissionKey, $isAdmin, $compId)`** เป็น coarse gate เดียวที่ใช้ทั้งระบบ ตาม convention เดียวกับ `PayrollRunModel::userCan()` เป๊ะๆ — `$isAdmin` bypass ทุกอย่าง (มาจาก `$_SESSION['user']['role'] === 'admin'`, ตัวเดียวกับที่ PayrollController ใช้) ไม่มี role ผูกกับ employee หรือ role ไม่มี grant ที่ตรง permission_key = deny
  - **Enforced จริงแล้วใน `SetupRulesController`** (holidayList/Get ต้อง `holiday.view`, holidaySave/Delete/ToggleStatus ต้อง `holiday.manage`, leaveType เหมือนกันกับ `leave_type.*`) **และ `ApprovalWorkflowController`** (workflowList/Get ต้อง `approval_workflow.view`, workflowSave/Delete/Duplicate/ToggleStatus ต้อง `approval_workflow.manage`, requestAct ต้อง `approval_request.act`, requestGet/List/Logs ใช้ `approval_workflow.view` ร่วม (ไม่มี permission แยกสำหรับ Monitor page เพราะ seed ไว้แค่ 8 ตัว)) — **`requestCreate()` ตั้งใจไม่ gate** เพราะเป็น API ที่โมดูลอื่นเรียกแทนพนักงานที่ยื่นคำขอ ไม่ใช่ action ตรงของ user ผ่าน UI นี้ และยังไม่มี flow จริงเรียกอยู่ดี (ดู bullet ด้านบนเรื่อง `ApprovalRequestModel` ยังไม่ผูก flow)
  - **`allow_scope='own_department'` บังคับใช้จริงแค่ `approval_request.act` เท่านั้น** — Holiday/Leave Type เป็น company-wide config table ไม่มี concept "record นี้เป็นของแผนกไหน" ให้ scope filter ได้จริง ตอนนี้ทั้ง schema/matrix UI ยัง support เลือก scope ได้ทุก permission (เผื่ออนาคต) แต่ enforcement ปฏิบัติกับ Holiday/Leave Type เหมือน scope='all' เสมอไม่ว่าจะตั้งอะไรไว้ — เขียนอธิบายไว้ตรงๆใน `PermissionModel` docblock ไม่ปล่อยให้เข้าใจผิดว่า enforce ครบ
  - **UI**: เพิ่มเป็น tab ที่ 6 "Permissions" ใน Company Setup → Organizational Structure (ข้างๆ Branch/Role/Department/Position/Rank) เพราะ role ถูกจัดการอยู่ตรงนั้นแล้ว ไม่สร้างหน้าใหม่แยก (`public/js/setup/permission-matrix.js`) เป็น checkbox matrix ธรรมดา (permission เป็นแถว, role เป็นคอลัมน์) **ไม่ใช่ DataTable** เพราะเป็น grid ตายตัว 8 permission ไม่ใช่ record list ที่ต้อง paginate — cell ของ `approval_request.act` มี dropdown เล็กๆ โผล่มาเมื่อติ๊กแล้ว ให้เลือก All/Own Department บันทึกทั้ง matrix ทีเดียว (`saveMatrix()` ลบ `role_permissions` ทั้งหมดของทุก role ในบริษัทแล้ว insert ใหม่ตามที่ติ๊กไว้ — replace ทั้งชุดเหมือน pattern อื่นๆ ในโปรเจกต์ ไม่ diff ทีละแถว) ถ้าบริษัทยังไม่มี role เลยจะโชว์ empty state ชี้ไปที่แท็บ Role
  - ทดสอบด้วย `tests/permission_matrix_test.php` (23 assertions: isAdmin bypass, deny เมื่อไม่มี grant/ไม่มี role, matrix()/saveMatrix() replace-semantics, validation ของ role_id/permission_id ที่ไม่ถูกต้อง) — **enforcement ที่ controller layer ไม่ได้ทดสอบผ่าน HTTP แบบ deny-path จริง** เพราะ dev session hardcode `role: 'admin'` ไว้ตลอด (bypass ทุกครั้ง) ทดสอบแค่ที่ `PermissionModel` โดยตรงแทน ซึ่งครอบคลุม logic เดียวกับที่ controller เรียกใช้
