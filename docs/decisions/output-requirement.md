## Output Requirement (Compliance)
- Export ภ.ง.ด.1 / ภ.ง.ด.1ก (กรมสรรพากร) ตามฟอร์แมตราชการ
- Export สปส. 1-10 (สำนักงานประกันสังคม) ตามฟอร์แมตราชการ
- Config ได้ต่อประเทศ เพราะ statutory ต่างกันตามประเทศ (TH/SG/MY/US)
- **Statutory export architecture** (`app/services/export/`): `StatutoryExportInterface` (contract) + `StatutoryExportRegistry` (lookup โดย code เช่น `TH_PND1K`, `TH_SSO110`) + implementation ต่อฟอร์แมตใน `app/services/export/{country}/`. เพิ่มฟอร์แมตใหม่ = เขียน class ใหม่ implement interface แล้ว register ใน `StatutoryExportRegistry::init()` บรรทัดเดียว ไม่ต้องแก้ของเดิม
  - **`PndOneKorExporter`/`Sso110Exporter` เป็น DRAFT ยังไม่ verified กับเอกสารทางการ** (ดึง field spec จาก PDF ทางการไม่ได้ในสภาพแวดล้อมนี้ — ข้อความไทยใน PDF สกัดไม่ออก ไม่มีเครื่องมือ OCR, และฝั่ง สปส. เพิ่งเปลี่ยนฟอร์แมต 1 ม.ค. 2569) แต่ละ class มี docblock ระบุว่าอ้างอิงจากแหล่งไหน มั่นใจแค่ไหน — **ห้ามใช้ output จริงในการยื่นจนกว่าจะเทียบกับเอกสารทางการแล้ว** (`isVerified()` คืน false อยู่)
  - `FixedWidthHelperTrait` มี helper สำหรับฟอร์แมต fixed-width (byte-based padding ไม่ใช่ char-based เพราะ Thai TIS-620 1 byte/ตัวอักษร vs UTF-8 3 bytes/ตัวอักษร)
  - ทดสอบด้วย `tests/statutory_export_test.php` (เช็คแค่ shape: ความยาว byte, delimiter, truncation — ไม่ได้ยืนยัน field content)
- **Reports module architecture** (`app/services/reports/`): `ReportGeneratorInterface` (contract: `code()`, `reportType()` = statutory/payment/internal, `label()`, `isVerified()`, `supportedFormats()`, `generate($context, $format)`) + `ReportRegistry` (lookup โดย code) + implementation แยกโฟลเดอร์ตาม report type (`statutory/{country}/`, `payment/`, `internal/`) เพิ่มรายงานใหม่ = เขียน class ใหม่ implement interface ครบ (รวม `isVerified()`) + register ใน `ReportRegistry::init()` บรรทัดเดียว ตอนนี้มีครบ 10 รายงาน: statutory 6 ตัว (`TH_PND1`, `TH_PND1K_SUMMARY`, `TH_SSO110`, `TH_SSO609`, `TH_KOR20KOR`, `TH_SLF`), payment 3 ตัว (`PAY_SLIP`, `BANK_TRANSFER_FILE`, `PAYMENT_VOUCHER`), internal 1 ตัว (`PAYROLL_REGISTER`)
  - **ใบแนบ ภ.ง.ด.1ก ไม่มี report แยกต่างหาก — `TH_PND1K_SUMMARY` (PDF/Excel) คือใบแนบอยู่แล้ว** เพราะ ภ.ง.ด.1ก ตัวจริงเป็นแค่ปกสรุปยอดรวม ส่วนตารางรายบุคคล (เลขผู้เสียภาษี/ชื่อ/เงินได้รวม/ภาษีหัก) ที่ต้องแนบคือ table เดียวกับที่ report นี้ทำอยู่แล้ว — ตอนตรวจสอบพบว่า logic มีอยู่แล้วแค่ label ไม่ได้บอกว่านี่คือใบแนบ จึงแก้แค่ label เป็น "ภ.ง.ด.1ก สรุปประจำปี (พร้อมใบแนบรายบุคคล)" ให้ discoverable ไม่ได้สร้าง class ซ้ำ
  - **`TH_SLF` (กยศ.) ไม่ใช่ statutory calc item แบบ SSO/PVD/PIT** เพราะยอดหักมาจากหนังสือแจ้งของกองทุนต่อพนักงานรายคน ไม่ใช่สูตร/เรทเดียวกันทั้งบริษัท จึงสร้างผ่านกลไก `payroll_earning_deduction_types` + `employee_earning_deductions` (installment-based) ที่มีอยู่แล้วสำหรับเงินกู้/เงินยืมพนักงาน — เพิ่มคอลัมน์ nullable `payroll_earning_deduction_types.statutory_report_code` (ตอนนี้มีค่าที่ valid แค่ `TH_SLF`) ให้บริษัท tag ว่า deduction type ไหนของตัวเองคือ กยศ. โดยไม่ต้องผูกกับ item_code/ชื่อที่ hardcode — ตั้งค่าได้ที่ Payroll Configuration > Earning-Deduction Types (field "Statutory Report Mapping" โชว์เฉพาะ item_type=deduction) `StudentLoanReport::generate()` หา item_code ที่ company tag ไว้ผ่าน `PayrollEarningDeductionTypeModel::itemCodesByStatutoryReportCode()` แล้ว filter `deduction_breakdown` ของแต่ละ run ด้วย code เหล่านั้น — ถ้าบริษัทยังไม่ tag อะไรเลยจะ throw `RuntimeException` บอกให้ไปตั้งค่าก่อน ไม่ generate ไฟล์เปล่า
  - เลขที่สัญญากู้ยืม (`employee_earning_deductions.external_reference_no`) มีอยู่ในสคีมาอยู่แล้วแต่ `EmployeeEarningDeductionModel::save()` ไม่เคยอ่าน/เขียนคอลัมน์นี้เลยมาก่อน (dead column) — wire เข้า save()/form ตอนทำ `StudentLoanReport` เพราะ report ต้องโชว์เลขสัญญาต่อพนักงาน ถ้าจะใช้ field อื่นที่มีในสคีมาแต่ไม่เคยต่อ UI ให้เช็คแบบเดียวกันก่อนสมมติว่ามันทำงานอยู่แล้ว
  - Query กลางที่รายงานทุกตัวใช้ร่วมกันอยู่ที่ `PayrollReportDataModel` (ไม่ใช่ query builder ต่อ type เพราะ query แต่ละรายงานต่างกันมาก แยกด้วย directory/class ต่อรายงานแทน) — มี `assertRunState()` บังคับว่า statutory/payment report ต้องอ่านจาก `payroll_runs.state` เป็น approved/paid/locked เท่านั้น (ตัวเลขที่ยัง draft แก้ได้อยู่ห้ามหลุดไปอยู่ในรายงานทางการ) ส่วน internal report (เช่น payroll register) เปิดให้ preview จาก draft ได้ — ข้อยกเว้นคือ `Sso609Report` ที่ query ตรงจาก `employees.employment_end_date` ไม่ผูกกับ run เลย (เป็น HR fact ไม่ใช่ตัวเลขที่คำนวณจาก payroll) จึงไม่มี state gate — `getRunDetails()` มี LEFT JOIN `master_banks` เพิ่มเข้ามา (คืน `bank_code`/`bank_name_th`/`bank_name_en`) สำหรับ `BankTransferFileReport`
  - Export ใช้ `dompdf/dompdf` (PDF) + `phpoffice/phpspreadsheet` (Excel) — เพิ่มเป็น composer dependency ตอนทำ Reports module (โปรเจกต์เดิมไม่มี PDF/Excel library เลย)
  - **PDF ภาษาไทยผ่าน dompdf (font `DejaVu Sans` ที่ bundle มา) verified แค่ว่า generate ไม่ error และขนาดไฟล์ปกติ — verify ด้วยตาจริงไม่ได้ในสภาพแวดล้อมนี้ (ไม่มี ghostscript/imagick แปลง PDF เป็นรูปให้ดู)** `pdftotext` ดึง text layer ภาษาไทยออกมาไม่ได้เลย (ตัวเลข/อังกฤษดึงได้ปกติ) — เป็น complex-script ToUnicode limitation ที่รู้จักกันทั่วไป ไม่ได้แปลว่าเรนเดอร์ผิดแน่นอน แต่ก่อนใช้ PDF จริงควรเปิดไฟล์ตัวอย่างดูด้วยตาก่อน ส่วน Excel (PhpSpreadsheet) verify แล้วว่า write/read ภาษาไทย round-trip ตรงทุกตัวอักษร (XLSX เก็บ UTF-8 ใน XML ไม่มีปัญหาเรื่อง font/glyph แบบ PDF)
  - **`ExcelRendererTrait::renderExcelFromRows()` ต้องเขียนทีละ cell ด้วย `setCellValueExplicit(..., DataType::TYPE_STRING)` เมื่อ value เป็น PHP string ห้ามใช้ `$sheet->fromArray()` ตรงๆ** เพราะ `fromArray()` auto-detect ค่า string ที่ "หน้าตาเป็นตัวเลข" (เช่น เลขประกันสังคม, เลขผู้เสียภาษี, เลขบัญชีธนาคาร) แล้วแปลงเป็น numeric cell type ให้เอง ซึ่งจะกิน leading zero ทิ้งถ้าค่าจริงขึ้นต้นด้วย 0 (เจอบั๊กจริงตอนทดสอบ `Sso609Report` — ค่าที่ควรเป็น string ดันถูก getCell()->getValue() คืนเป็น int) ค่าที่เป็น PHP float/int จริง (เช่นยอดเงิน) ยังปล่อยเป็น numeric ตามปกติเพื่อให้ Excel sum/format ได้
  - `PndOneKorSummaryReport`/`PndOneReport` (statutory) ใช้ซ้ำ `PndOneKorExporter`/`PndOneExporter` จาก export module เดิมสำหรับ format `txt` (ไม่เขียน pipe-format ซ้ำ) ส่วน pdf/excel เป็น layout สรุปของระบบเองไม่ใช่แบบฟอร์มราชการ เช่นเดียวกับ `Sso110Report` ที่ใช้ซ้ำ `Sso110Exporter` สำหรับ `txt`
  - **`BankTransferFileReport` ออกเป็น CSV รูปแบบเดียว (generic) ไม่แยกตาม `payroll_cycles.bank_file_format_id`** เพราะยังไม่ได้ไปหา spec จริงของแต่ละธนาคารมาเทียบ (4 แถวใน `master_bank_file_formats` เป็นแค่ placeholder ไม่มี real spec รองรับ) — พนักงานที่ไม่มีข้อมูลธนาคารครบจะถูกข้ามพร้อม comment แจ้งเตือนในไฟล์ ไม่ใช่หายไปเงียบๆ ถ้าจะทำแยกตามฟอร์แมตธนาคารจริงต้องหา spec มาก่อน
  - `Sso609Report`/`Kor20KorReport` (statutory, DRAFT) **ไม่มี format `txt`** ต่างจาก PND1/PND1K/SSO110 เพราะไม่มี field-layout ใดๆ ให้อ้างอิงเลย (ยังไม่เคยหา spec อิเล็กทรอนิกส์ของฟอร์มนี้เจอ) รองรับแค่ pdf/excel เป็น human-readable summary
  - ทดสอบด้วย `tests/reports_test.php` (สร้าง run จริงผ่าน `PayrollRunModel` จนถึง approved แล้วเรียก generator จริงทุกตัว รวมถึงเช็คว่า state gate บล็อก draft run ได้จริง) — fixture มีพนักงาน 2 คน คนที่สองจงใจตั้ง `employment_end_date` เป็น "เดือนก่อนหน้า" ไม่ใช่เดือนเดียวกับ run หลัก เพื่อไม่ให้ eligibility-by-date-range ของ `PayrollRunModel::recalculate()` ดึงเข้ามาคำนวณในตัวเดียวกันโดยไม่ตั้งใจ (ถ้าตั้งช่วงวันที่ทับกัน จะพังทั้ง employee_count และลำดับ array ของ test อื่นๆ ที่ expect พนักงานคนเดียว)
  - **ไม่มี report_schedules/config table** (ตกลงกันไว้ตอน schema step ว่าเอา on-demand generate ก่อน) — `report_export_logs` เป็น audit log อย่างเดียว (log/list เท่านั้น ไม่มี update/delete เหมือน `payroll_run_audit_logs`) รองรับ filter ตาม report_type/period_year/period_month/payroll_run_id/format ทุก report generator ต้อง validate `context` เอง (ไม่ใช่ที่ controller) แล้ว throw `InvalidArgumentException` (input ผิด) หรือ `RuntimeException` (ข้อมูลไม่พบ/ไม่มีสิทธิ์ตาม state) ให้ชัดเจน — ห้าม generate ไฟล์เปล่าเงียบๆ เวลาไม่มีข้อมูล (เช่น ปีที่ไม่มี run approved เลย ต้อง error ไม่ใช่คืนไฟล์ 0 แถว)
