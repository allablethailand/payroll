## Document Requests — Employment Certificate Request/Approval/Issuance + shared timeline UI (`Payslip & Documents` menu → "Requests" page, 2026-08-26)
- **Explicit request: "ในส่วนของ Request เพิ่ม Tab สำหรับการ Request ใบรับรองขึ้นมาด้วยคู่กับ Pay slip และการอนุมัติให้เป็นรูปแบบเดียวกับ Approve Process ครับมี timeline ให้กดดู"** — add a 3rd tab on the existing Payslip Requests page (`payslip-documents/requests`) for requesting an Employment Certificate, paired with the existing Payslip Requests tab, and restyle the approval detail view to look like the Payroll Approve Process page's timeline. Two AskUserQuestion decisions confirmed upfront: (1) approval **auto-generates the real PDF** (not just a status flag) — this is the recommended, chosen option, mirroring how Payslip Request auto-sends on approval; (2) the design upgrade applies to **BOTH** tabs (Payslip Requests' existing plain-list timeline gets upgraded too, not just the new Certificate tab).
- **`employment_certificate_requests`** (new table) is a direct structural port of `payslip_requests`' own paired-row architecture (see that model's docblock) — `comp_id`/`employee_id`/`language` (`th`/`en`)/`requested_by`/`approval_request_id` (unique, FK → `approval_requests`)/`status` (`pending`/`approved`/`rejected`/`cancelled`/`issued`/`issue_failed`)/`file_path`/`issue_error`. `EmploymentCertificateRequestModel::create()` validates the employee exists, the language is valid, no OTHER pending request already exists for that SAME employee+language (a pending request for the other language is NOT a duplicate — each language is issued/approved independently), **and confirms a real template already resolves for this employee+language via `EmploymentCertificateTemplateModel::resolveTemplateForEmployee()` before ever creating the row** — this is deliberate: a request must never be able to reach "approved" and then dead-end at issuance time because nobody set up a template, so the check happens up front at request time instead. Then inserts the row, calls the generic `ApprovalRequestModel::create($compId, 'EMPLOYMENT_CERTIFICATE_APPROVAL', $requestId, $label, $requestedBy)`, and links `approval_request_id` back — same one-owned-transaction pattern as `PayslipRequestModel::create()`. `EMPLOYMENT_CERTIFICATE_APPROVAL` was seeded config-only back in Employment Certificate Template's own v4 (see that section) with no consumer yet — this is its first real consumer, so any company that hasn't configured an ACTIVE workflow for this document type yet will get `create()` failing with "No active workflow is configured for this document type yet." (the generic engine's own message) until one is set up in Approval Workflow settings' 3rd pill.
- **Two-phase status, same pattern as Payslip Request's `approved`→`sent`/`send_failed`**: the generic engine's terminal verdict (`approved`/`rejected`/`cancelled`) is phase one; `EmploymentCertificateRequestModel::syncFromApprovalStatus()` (called from `ApprovalWorkflowController::syncDocumentAfterAct()`'s new `case 'EMPLOYMENT_CERTIFICATE_APPROVAL'`, kept OUT of `ApprovalRequestModel` itself to preserve its document-type-agnosticism) is phase two — on `approved` specifically, it calls a private `issuePdf()` which re-resolves the template (defensively — it could have been deleted between request and approval), renders via a new `EmploymentCertificateRenderer::renderForIssuance()`, writes the PDF to `public/uploads/employment_certificate_files/{comp_id}/{32-hex}.pdf`, and lands the row at `issued` (or `issue_failed` with a reason in `issue_error` on any handled failure — a rendering/disk error must never silently undo the approval decision itself, same "best-effort, wrapped in an outer catch" precedent as `PayslipDeliveryService::deliverForRequest()`). **Generated ONCE, at approval time, never re-rendered afterward** — a later edit to the employee's data or the template must not retroactively alter an already-issued legal document. `EmploymentCertificateRequestController::download()` streams the file back with `realpath()` path-containment validation (same pattern as every other file-serving endpoint in this app) and only for `status='issued'`.
- **Shared generic approval-detail timeline** (`public/js/setup/approval-request-detail.js`, new file) — extracted OUT of `payslip-request.js` (where the modal used to live as a plain bordered list) into its own file so BOTH the Payslip Requests tab and the new Employment Certificate Requests tab share ONE `#requestDetailModal` + ONE set of rendering functions, driven only by an `approval_request_id` and the generic engine's own endpoints (`GET api/approval-request.get`/`.logs`, `POST api/approval-request.act`) — **deliberately NOT modeled on `public/js/payroll/approval.js`'s own `.apv-*` timeline**, which is tightly coupled to `payroll_run_audit_logs`/`PayrollRunModel::approvalFlow()` and has no equivalent for an arbitrary `approval_request_id`. Same VISUAL language reused on purpose (colored circular stage marker + connecting line + title/badge/body, new `.art-*` CSS classes in `style.css`, deliberately a separate classname set since the shape is simpler — no per-approver "substep" concept) but oldest-stage-first (Requested at the top), not reversed like `.apv-*`, since it just appends each `approval_request_logs` row in the order the API already returns them. `openApprovalRequestDetail(id, onActed)` takes a reload callback so the caller's own DataTable can refresh itself after an approve/reject/cancel without this shared file knowing which table is open.
- **Employment Certificate Requests tab** (`public/js/setup/employment-certificate-request.js`, new file, `#tb_ecr_request`) mirrors `payslip-request.js`'s own DataTable structure — the one real UI difference is its status badge has 2 extra states (`issued`/`issue_failed`, Payslip's own equivalent is `sent`/`send_failed`) and its action column gets a Download button once `status='issued'`. **Initializes its DataTable only on `shown.bs.tab`, never immediately on page load** — unlike Payslip Requests (this page's default-active tab), this one starts hidden, and this app has hit the "`responsive: true` DataTable inside a `display:none` Bootstrap tab collapses every column to 0 width" bug enough times elsewhere that it's now a standing habit to check for on any non-default tab. The request-creation modal's employee picker reuses the existing generic `POST api/employee.report_to.get` endpoint as-is (same reuse precedent already established for Payslip/Employment Certificate Template's own "Assign To" pickers) rather than building a new one.
- **Page header generalized** — `requests.php`'s `.page-header-card-title`/`-desc` moved off the `payslip_requests` i18n key (that key is now ONLY the Payslip Requests tab button's own label) onto new dedicated `document_requests_title`/`document_requests_description` keys, so the page-level heading doesn't misword itself as payslip-only now that it covers two document types.
- Tested with `tests/employment_certificate_request_test.php` (31 assertions, new file, direct structural mirror of `tests/payslip_request_test.php`) — unknown employee/invalid language/no-template-yet/no-active-workflow-yet all rejected in the right order, duplicate-pending-per-language rejected while a different language for the same employee is correctly NOT treated as a duplicate, `approval_request_id` correctly links both directions, full approve→issued flow verified against a REAL PDF file written to disk (asserts `is_file()` + the bytes actually start with `%PDF`, not just that the DB row changed) with the file cleaned up in a `finally` block since a rolled-back transaction cannot undo a real `file_put_contents()`, reject/cancel flows, and `list()`. Isolation follows the same established pattern as `tests/employment_certificate_template_test.php`/`tests/payslip_request_test.php`: comp_id=1 is the real, live dev DB, so any active `employment_certificate_templates` and any active `EMPLOYMENT_CERTIFICATE_APPROVAL` workflow are temporarily cleared inside this test's own rolled-back transaction before the fixture builds its own. Full regression suite re-run clean (same 2 pre-existing, unrelated dev-DB-drift failures in `master_data_sync_test.php`/`permission_matrix_test.php` as every other round in this project, neither touched here). The timeline/DataTable/modal JS itself has no PHP test coverage (same standing limitation as every other canvas/interaction feature in this project) — verified by cross-checking every new JS id/class selector against the actual view markup, not by clicking through a real browser.
- **2026-08-26, same-day follow-up: Delivery Log tab unified to cover BOTH document types, filter UI restyled to match Employee List (explicit request: "ช่องประวัติการส่งปรับ Filter ให้เหมือนหน้าพนักงาน และมีเพิ่มประเภทเอกสารที่ส่งด้วยครับ")** — confirmed via AskUserQuestion that "เพิ่มประเภทเอกสารที่ส่ง" meant genuinely folding Employment Certificate issuance INTO the log (not just adding a filter dropdown that would only ever have one real value, since `payslip_delivery_logs` only ever logged payslip sends before this).
  - **New `DocumentDeliveryLogModel`** (`app/models/`, new file, does NOT touch `PayslipDeliveryLogModel`/`payslip_delivery_logs` at all) — a `UNION ALL` at the READ layer combining `payslip_delivery_logs` (JOINed to `payroll_runs`, unchanged) with `employment_certificate_requests` WHERE `status IN ('issued','issue_failed')` (a `pending`/`approved`/`rejected`/`cancelled` request was never actually attempted-to-issue, so it must never appear in an issuance log). Deliberately a union at the read layer rather than widening `payslip_delivery_logs`' own schema — that table's shape (`run_id NOT NULL`, `channel_code`/`recipient`, a real "send via a channel with a fallback chain" concept from `PayslipDeliveryService`) genuinely doesn't fit a certificate (no channel, no recipient address, no retry-the-fallback-chain, generated ONCE at approval time) — same "combine at the read layer, don't force a shared write schema" precedent `PayrollReportDataModel` already established for the Reports module's own varied sources.
  - Normalizes both sources to one row shape: `document_type` (`payslip`/`employment_certificate`), `status` (`success`/`failed` — a certificate's own `issued`/`issue_failed` is mapped via `CASE` in the SQL itself, not in PHP), `channel_code`/`recipient` (payslip-only, `NULL` for a certificate — there is no channel/recipient concept for an auto-generated file), `sent_by`/`sent_by_name_*` (payslip-only, `NULL` for a certificate — nobody "sends" it, the system issues it automatically on approval), `source` (`auto`/`request` for payslip, always `request` for a certificate since there is no auto-issuance path), `reference_label`/`period_start_date`/`period_end_date` (payslip's pay period, `NULL` for a certificate), `language` (`th`/`en`, certificate-only, `NULL` for payslip). A row's own `id` still belongs to whichever source table it came from (`payslip_delivery_logs.id` or `employment_certificate_requests.id`) — callers MUST branch on `document_type` before using `id` against an action endpoint, never assume one shared id space.
  - **New `DocumentDeliveryLogController@list`** (`GET api/document-delivery-log.list`) is the tab's new data source, replacing `api/payslip-delivery-log.list` for the LIST call only — `PayslipDeliveryLogController`/its own `api/payslip-delivery-log.list`/`.resend` endpoints are UNCHANGED and stay live, since Resend is still payslip-only logic against the original table. Download for an issued certificate row reuses the EXISTING `api/employment-certificate-request.download?id=` endpoint as-is (same one the Employment Certificate Requests tab already uses) — no new download endpoint needed.
  - **Filter UI restyled to Employee List's own collapsible `.station-filter` pattern** (see `app/views/employee/list.php`) instead of the old plain `.row.mb-3.g-2` of 3 bare dropdowns — corner "Filter" label + collapse/expand chevron toggle, a "Clear Filter" button that only shows once a filter is actually active, same show/hide-by-`hasFilter`-check + `.station-filter.collapsed` CSS this app already uses on the Employee page and the Payroll Process page. A new 4th filter, **Document Type** (`select2-static`, `doc_type_payslip`/`doc_type_employment_certificate` i18n keys — the second one newly added, mirroring the Document Numbering module's existing `doc_type_payslip` wording), joins the existing Status/Channel/Source filters.
  - Table gained a **Document Type** column (right after Employee) and its old **Pay Period** column was generalized to **Reference** (reused the existing `reference` i18n key, same one the Approval Request timeline already uses) — shows the pay period for a payslip row, or the certificate's language (Thai/English, reusing the SAME `template_language_th`/`template_language_en` labels the Employment Certificate Requests tab's own language cell already uses) for a certificate row. The Actions column branches on `document_type`: a failed **payslip** row still gets the existing Resend button (unchanged `PayslipDeliveryService::resend()` retry-the-fallback-chain behavior); an issued **certificate** row gets a Download button instead; a failed certificate row (`issue_failed`) gets no action here (retrying/re-issuing a failed certificate was not part of this request — out of scope, same as it already was on the Requests tab, which also has no retry action for `issue_failed`).
  - Tested with a new `tests/document_delivery_log_test.php` (20 assertions) — a real payslip delivery fixture (via `PayslipDeliveryService::deliver()`, 2 failed fallback attempts) alongside 3 directly-inserted `employment_certificate_requests` rows (issued/issue_failed/pending), confirming: no-filter returns exactly the 2 terminal cert rows + 2 payslip rows (the `pending` cert row never appears), `document_type` narrows correctly both ways, `status` normalizes and combines correctly across both source tables (`success`=1, `failed`=3), `channel_code=email` doesn't leak in a certificate row (certificates have no channel), and the `employees`/`sent_by` joins resolve correctly for both branches (`sent_by_name_th` is `NULL` for a certificate, confirming nobody-sends-it is represented correctly, not just defaulted by an accidental join failure). Isolates its own fixture rows from concurrent real dev-DB data by filtering the returned array down to its own fixture `employee_id`s locally (this model has no `employee_id`/`run_id` filter of its own by design), rather than trusting raw counts — see `feedback_dev_db_shared_state_test_fragility` memory. Full regression suite re-run clean (same 2 pre-existing, unrelated dev-DB-drift failures only).
