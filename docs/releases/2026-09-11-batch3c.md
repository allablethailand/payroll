## What changed, by item

Task order for this batch: **3 → 9 → 7 → 5 → 2 → 1 → 8 → 4 → 6**.

**Item 3 — Employee avatar click in List (`f026bdb`)**
- Real bug fixed: `.emp-avatar-link`'s click handler was delegated on `document` in the bubble phase, so a closer row-click handler (navigating to the run's Detail page) fired first regardless of source order — `stopPropagation()` inside the avatar handler was too late to stop it. Fixed by switching to the native **capture phase** (`addEventListener('click', ..., true)`), so this one central handler always sees the click before any bubble-phase row handler on any page gets a chance.
- Avatar size in the Process List's "Updated By" column increased 24px → 32px.

**Item 9 — Verify/Unverify buttons (Detail › Employee tab) (`b42b70f`)**
- Unverify now confirms before acting (previously skipped confirm entirely) — both directions use a dedicated SweetAlert2 confirm naming the employee and the actual action label, not a generic "OK".
- Bulk Verify gained a confirm dialog (previously fired immediately) whose title fills in the real selected count via a `{count}` placeholder.

**Item 7 — Employee tab column changes (`03d1e2a`)**
- Removed the "Source" column, replaced with a 3-way filter pill (All/Sync/Manual) above the table.
- Added a **Department** column in the Source column's old slot.
- New BACKLOG entry opened (see below) — a real gap found while touching Department resolution: it's a live join to the employee's *current* department, not a snapshot as of the run.

**Item 5 — Hide empty tabs (`5579a91`)**
- Cash Payments / Bank Account Assignment / Third-Party Remittance tabs on Detail now hide entirely when the run has nothing for them (instead of showing an empty state). Computed from the existing `run.details[]` payment-method breakdown (Cash/Bank) plus a new `PayrollRunModel::get()` field, `remittance_count` (a real `COUNT()` against `payroll_remittances`, since remittance rows aren't reachable from `getDetails()` at all).
- If the currently-active tab gets hidden this way, switches to the Employee tab automatically.

**Item 2 — Action History tab (`0761a87`)**
- Raw `user_agent` strings now render as a compact "OS · Browser major-version" summary (e.g. "Windows 10 · Edge 152") instead of the full UA string inline (still available via tooltip).
- New client-side `parseUserAgent()`/`formatUserAgentSummary()` (app.js), deliberately kept in lockstep with `EmployeeLoginLogModel::parseUserAgent()`'s own PHP regex/ordering (Edge/Opera checked before Chrome/Safari — both embed those tokens) since this page renders raw, unparsed audit-log UA strings rather than pre-parsed columns.
- New `tests/user_agent_parser_test.js` (25 assertions, plain Node, no framework — matches this project's own `tests/*.php` PASS/FAIL convention since `app.js` itself can't be `require()`'d directly).

**Item 1 — Unify approval timeline modal (`bcb07d9`)**

- New **"Submitted"** stage added between Created and Approval, showing who submitted and when — reuses the existing `runLifecycleSteps()`'s `pending_approval` entry (no new date/action mapping).
- Resolves the standing BACKLOG entry "Consolidate `apvApproverSubstepHtml*` (Rd/Pr/Ap) into app.js" (originally Batch 2 item 2) as a side effect.

**Item 8 — Employee header card on every employee-row modal (`519aa30`)**

- New shared `runDetailRowByEmployeeId()` helper generalized out of 4 identical copies of "find this employee's row in the currently-loaded table data" (per this project's own "generalize, don't mirror-copy" rule) rather than adding a 5th copy for the new Comments handler.
- `PayrollReportDataModel`/`PayrollRunEmployeeBankAccountModel`/`PayrollRunModel` each gained the extra SELECT columns (profile photo, department/position names) these cards need.

**Item 4 — Payroll Run field locking (decision 2 + sub-steps 4a–4d, `b470a17`/`34935eb`/`9822ee3`/`e0bbc4d`+`c04f204`/`c6e1c41`)**

*Decision 2 (`b470a17`) — `hasAdminWork()`-based field lock, replacing an initially-considered `employee_count`-based rule (rejected: a sync-linked run's `employee_count` is already >0 the instant it's created, which would have locked `run_purpose`/flags before the admin ever got to adjust them on Edit).*
- `PayrollRunModel::get()` now attaches `has_admin_work`/`admin_work_summary` (itemized: manually-joined employees, adjustments, verified employees, comments, genuinely admin-triggered recalculates — excluding the one automatic recalculate `create()` fires for a sync pull) to every run row it returns.
- New `runFieldLockState(run)` — the ONE function used both to render (disable fields + helper text) and to validate server-side. Lock tiers: `source` always immutable; `cycle_id`/`period_dates`/`run_purpose`(+flags)/`merge_target` locked once the run leaves draft OR has admin work; `run_name`/`payment_date`/`use_flat_tax_rate` locked only once the run leaves draft; `notes` never locked (a genuine capability expansion — `update()` used to refuse ANY edit once state left draft).
- Server-side enforcement (`applyFieldLocks()`) **skips just the locked field group** and reports it, rather than rejecting the whole save — deliberate, since sub-step 4a/4b's client-side lock mirror didn't exist yet at this point in the batch, so every save from the not-yet-merged form resent every field regardless of lock state.

*Sub-step 4a (`34935eb`) — merged the separately-maintained `#editRunForm` (detail.php) into the Create flow's `#payrollRunModal`, one shared form for both.*
- Edit now populates `#run_id` (empty = create, real id = update) and every field through the same shared app.js functions Create already used, replacing a byte-for-byte duplicate modal/form/JS set.
- `#run_merge_target_id`'s options gained `data-exclude-id` (Edit: this run's own id, so it never lists itself; Create: cleared).

*Sub-step 4b (`9822ee3`) — JS mirror of `runFieldLockState()` + `skipped_fields` SweetAlert notice + recalc-needed warning.*
- `applyRunFieldLockUi(run)` disables every locked field group and shows one combined summary explaining why (reusing the richer server-computed `admin_work_summary`, not a generic sentence repeated per field).
- A save whose response includes `skipped_fields` now shows a SweetAlert listing each skipped field's reason.
- New recalc-needed warning: if a draft run with `employee_count > 0` had `run_purpose`/its 4 calc flags changed on save, warns the admin to hit Recalculate themselves (decided explicitly NOT to auto-recalculate here — see BACKLOG below).

*Sub-step 4c (`e0bbc4d` main feature + `c04f204` same-day review follow-up, merged via `9987c5f`) — unify `use_flat_tax_rate` visibility rule (Decision 1: "show when run is Incentive/partial AND tax_treatment='separate', regardless of source; PHP must reject the value if the condition doesn't hold").*
- `PayrollRunModel::get()`/`create()` now expose `sync_attribution_tax_treatment` (from `payroll_sync_processes.attribution_tax_treatment`) — never exposed before.
- New private `useFlatTaxRateAllowed($runPurpose, $attributionTaxTreatment)`: `incentive AND (attribution ?: 'separate') !== 'merge'` — no attribution at all (manual run, or an unattributed pull) defaults to effectively `'separate'`.
- `create()`/`update()` both now gate `use_flat_tax_rate` through this helper — **the backend never validated tax treatment at all before this**, relying entirely on the client's own show/hide. A rejected `true` is forced to `0` and reported via a new shared `flatTaxNotAllowedSkipEntry()` into `skipped_fields` (reason `flat_tax_not_allowed`) — `create()` gains a `skipped_fields` key in its response for the first time.
- Follow-up review (`c04f204`, no code changes to the rule itself) confirmed both enums involved are fully accounted for (`run_purpose` has no 'partial' value distinct from 'incentive'; `attribution_tax_treatment` is `enum('merge','separate')` NULL only) and flagged a separate, unrelated `payroll_earning_deduction_types.tax_treatment` enum as not a competing implementation. Also wired the SweetAlert notice to look up an i18n-translated reason message (`run_field_lock_reason_<reason>`) before falling back to the server's hardcoded English text — as a side effect, the 3 pre-existing lock reasons from decision 2/4b now get real i18n translation for the first time.

*Sub-step 4d (`c6e1c41`) — final sub-step of item 4: opened Edit for every run state, widened the recalc-warning comparison.*
- `#btnEditRun` no longer gated to draft-only — moved its `.append()` above the early `if (run.state !== 'draft') return;` gate (every other draft-only control in the same function stays behind it). `applyRunFieldLockUi()` already handles a non-draft run correctly (locks everything except `notes`).
- Recalc-needed warning widened to also compare `cycle_id` and both period dates, alongside `run_purpose`+flags — all three groups share the identical tier-2 lock condition.

**Item 6 — DataTable-ify remaining Detail page tabs (`81a3e61`)**
- Surveyed all 9 tables on the Detail page first; 5 were already DataTables or confirmed out-of-scope modal drill-downs (user-confirmed via AskUserQuestion). Converted the remaining 4: Reports, Cash Payments, Bank Account Assignment, Third-Party Remittance.
- New shared `initSharedDataTable(selector, options)` (app.js) — the one generic initializer this item asked for. Owns the destroy/render/construct order via a required `renderRows` callback (real bug caught and fixed during review — see below).
- `getTableLang()` gained a genuinely-missing `emptyTable` key (added to both lang files too).
- `data-order` attributes added to money/date columns so DataTables' HTML5 auto-detection sorts them numerically/chronologically instead of lexicographically on the formatted display text.

## Bugs found along the way

- **Employee avatar click firing the wrong navigation** (item 3) — bubble-phase delegation on `document` lost the race to a closer row-click handler; fixed with capture-phase.
- **Unverify skipped confirmation entirely** (item 9) — now confirms both directions.
- **`use_flat_tax_rate` had zero server-side validation before this batch** (item 4, decision 1/4c) — the backend trusted the client's own show/hide completely; a crafted or stale request could set it `true` under any circumstance.
- **The first version of the field-lock rule (decision 2) would have locked a fresh sync pull's `run_purpose`/flags immediately** — caught before shipping by reasoning through `employee_count`'s own timing, corrected to the `hasAdminWork()` rule before any code landed on that approach.
- **The first version of server-side lock enforcement rejected the whole save on any locked-field attempt** — corrected to skip-and-report per field group, since the client-side lock mirror (4b) didn't exist yet at that point and would have made the form briefly unusable.
- **`getTableLang()` was missing an `emptyTable` key** (item 6) — confirmed via grep, neither lang file had it either; a zero-row DataTable using the new shared initializer without a per-call override would have shown DataTables' own unlocalized default.
- **DataTables destroy-before-render ordering bug** (item 6, caught by the user's own review, not autonomously) — calling `.html(newRows)` before `.DataTable({destroy:true})` let `destroy()`'s own tbody-restore-from-cache silently overwrite the fresh rows. Fixed by having `initSharedDataTable()` own the whole clear→destroy→render→construct sequence internally.
- **Money/date columns in the 4 newly-DataTable-ified tables would have sorted lexicographically** (item 6, caught by the same review) — fixed via `data-order` attributes, verified against the actual bundled DataTables source that this needs zero `columns:[]` config.

## Backlog added this batch

- **Snapshot department/position onto the run row at lock (or pull-in) time** (item 7) — Department (and Position, in the Payroll Register export) is resolved via a live join to the employee's *current* structure, not a snapshot as of the run; a later transfer/reorg silently rewrites how an old, already-paid run displays. Needs a migration + a decision on when to snapshot (pull-in vs. lock time) — scoped as its own task.
- **`payroll_run_audit_logs` has no auto/admin trigger-type distinction for `recalculate`** (item 4 decision 2) — `adminRecalculateCount()`'s "count then subtract 1 for the automatic one" heuristic only works because there's currently at most one automatic recalculate per run (at creation); would silently undercount if a future feature adds a second automatic recalculate elsewhere in the lifecycle. Low priority; would need a migration (`trigger_type` column).
- **`PayrollRunModel::update()` doesn't auto-recalculate after a `cycle_id`/period/`run_purpose` change on a no-admin-work draft** (item 4 decision 2 follow-up) — decided explicitly NOT to auto-recalculate; sub-step 4b's client-side warning (tells the admin to hit Recalculate themselves) is the shipped mitigation instead. No schema/backend change.
- **Remittance Breakdown modal: consider DataTable if rows exceed 5** (item 6) — confirmed via AskUserQuestion to stay a plain `<table>` for now, alongside the other 3 modal-internal drill-downs; unlike those 3 (fixed-field forms with no realistic growth), a company with many loan/remittance creditors on one employee could genuinely exceed a handful of rows. Deferred to the phase design pass, not converted pre-emptively with no evidence it's needed — would reuse `initSharedDataTable()` (added this same batch) if picked up.
- (Resolved, not added, this batch: the standing "JS/lang cache-busting" backlog item and "langReady-gating not applied to 28/29 files" backlog item — both closed out via the `0b48b46`/`2e7b2f5` commits at the start of this range; see `BACKLOG.md`'s own updated entries for detail. Also resolved: "Consolidate `apvApproverSubstepHtml*` into app.js", Batch 2 item 2, closed as a side effect of item 1's timeline-modal unification.)
