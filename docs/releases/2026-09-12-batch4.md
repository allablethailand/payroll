**Item 1 — Lang file dedup + check-lang wired into the test suite (`8911860`)**
- New `scripts/check-lang.php`: a hand-rolled JSON tokenizer/parser (not `json_decode()`, which silently keeps only the last occurrence of a duplicate key) that surfaces every duplicate key and any key present in one lang file but missing from the other.
- Removed the first (dead) occurrence of 10 duplicate keys in both `th.json`/`en.json` (`allowed`/`yes`/`no`/`bank_account`/`amount`/`add_item`/`total_days`/`table_frequency`/`reject_modal_title`/`source`) — the second occurrence (already what every page actually renders) is kept, so no behavior change.
- `confirm_revert_message` split into a new `confirm_revert_to_draft_message` (both real call sites, `payroll/approval.js`/`payroll/detail.js`, updated) since it genuinely needed the statement form, not the question form — the old key removed entirely rather than left holding an unused value.
- Removed a stray root-level `default_label` key in `th.json` (an accidental duplicate of `tax.default_label`, unreferenced anywhere; `en.json` never had it).
- `check-lang.php` refactored into a reusable `checkLangFiles()`/`printLangCheckReport()` library + a CLI-only report block, so the new `tests/lang_check_test.php` (5 assertions) reuses the same parser instead of duplicating it.

**Item 2a — statutoryRateModal's Item Details form vanishing on repeat open (`bb0a030`)**
- Real bug, root cause confirmed by reading the bundled `bootstrap.js` source directly: `openStatutoryRateModal()` manually stripped `active`/`show` off the tab-**panes** only, never the matching trigger **button** — Bootstrap's own `Tab.show()` checks the button's `active` class, so once it carried `.active` from an earlier open (nothing ever cleared it on close), `.show()` silently no-opped on every subsequent open, leaving the pane it had just deactivated by hand permanently empty.
- New shared `public/js/app.js::resetModalTabs($modal)` resets every tab trigger button AND its pane together, as a pair, for any Bootstrap-tabbed modal — a bug class any modal in this app could hit the same way. Grepped the rest of `public/js` for the same pane-only-strip pattern; no other occurrence found.

**Item 2b — Tax & Statutory "Manage" tooltip clarity (`32caca6`)**

Per T046's own prior deliberate decision to merge Edit+Manage into one button, a dedicated pencil "Edit" button was proposed and declined — fixed as a discoverability-only tooltip change instead (`sr_edit_or_manage_rates`, custom rows only; master rows keep the plain "Manage" tooltip).
- New BACKLOG entry opened for a phase-design pass reviewing row-action icon/tooltip clarity app-wide (this fix covered one page only).

**Item 3 — Employee SSO/PVD dependent-field gate (`06f8ec0`)**
- Employee Detail's ประกันสังคม/กองทุนสำรองเลี้ยงชีพ section let dependent fields (Hospital, all 9 PVD detail fields, สปส.6-09 leave reason) stay visible and savable regardless of the "Enrolled" toggle — PVD had no visibility gate at all. Server-side, `EmployeeModel::save()` accepted and persisted these fields unconditionally, with no awareness of the company-level `company_statutory_settings` toggle either.
- New `CompanyStatutorySettingModel::effectiveStatusForItemCode()` (generalized from the existing `list()`/`get()` resolution), `StatutoryCalculationEngine::ITEM_ENROLLMENT_FLAG` made `public` (single source of truth for item-code → employees-column, reused instead of a second map).
- `EmployeeModel::save()` now silently strips (no validation error) any SSO/PVD dependent field the employee isn't enrolled in OR the company hasn't turned on — on UPDATE the row's existing value is preserved (never deleted), on CREATE it stays null. `sso_no`'s ciphertext is carried over as-is (never re-encrypted). `sso_leave_reason_code` additionally requires `employment_status` to be resigned/terminated.
- New `EmployeeModel::statutoryEnrollmentGateInfo()` is the one place both server validation and the client JS read this gate from, so they can never disagree.
- `detail.php`/`detail.js`: PVD fields wrapped in a new `#pvdDetailFields` (previously ungated entirely), Hospital moved inside `#ssoDetailFields`, the whole SSO/PVD column replaced by an explanatory message when the company hasn't enabled the item (2 distinct wordings: not configured vs. not applicable to the company's country), hidden fields are cleared in the DOM (not just hidden), since `collectEmployeeFormData()` submits every `[name]` regardless of `.d-none`.
- New `tests/employee_statutory_enrollment_gate_test.php` (39 assertions). `tests/company_lookup_list_test.php` updated to submit `sso_enrolled`/`pvd_enrolled` explicitly.
- Excel import path investigated and confirmed not to exist — nothing to wire there. Origami sync path (which writes `sso_*` via raw SQL, bypassing this gate) deliberately NOT touched this round, per explicit instruction — flagged in BACKLOG (see below).

**Item 4 — Employee Recheck tab filters + `is_payroll_ready` drift investigation (`0b21d7a`)**
- `/employees#employee-recheck-top-tab` only exposed View/Role/Department/Team/Shift/Branch as filters, even though `EmployeeModel::buildListWhere()` already supported more. Added the remaining enum/lookup columns this table displays — Status, Employment Status, Position, Nationality, Tax Calculation Method, Payment Method — reusing the exact same filter pattern already on the page (no new filter mechanism). Final UI order (12 filters total): View, Status, Employment Status, Department, Team, Position, Branch, Shift, Role, Nationality, Tax Method, Payment Method.
- `buildListWhere()` also gained `is_ready` (filters the persisted `employees.is_payroll_ready` column) — added to the backend/tests but **NOT exposed in the UI this round**, after a real drift investigation (see below) found the column can't currently be trusted for sync-written employees.
- Investigation, not guessed: `EmployeeSyncer::upsertItem()`/`PayrollSyncModel::applyOneEmployeeMasterFields()` (both Origami sync paths) write readiness-affecting fields via raw SQL that bypasses `EmployeeModel::save()` entirely and never recomputes `is_payroll_ready`. A prototype `EmployeeModel::recomputeIsPayrollReady()` (reusing `save()`'s own `isPayrollReady()` definition, no second rule) was wired into 3 sync call sites and then **reverted** after it broke `tests/payroll_sync_attribution_test.php` (23 failures) — root cause: that fixture (and, very plausibly, real Origami-synced employees) only ever appeared "ready" by riding the schema's own `is_payroll_ready DEFAULT 1`, never actually satisfying `requiredColumns()`. Turning the recompute on for real would flip a nontrivial number of real synced employees, company-wide, from a false-positive Ready to the true Not Ready — a business decision, not a safe drop-in fix.
- The method itself (`recomputeIsPayrollReady()`) stays in `EmployeeModel.php`, **unwired/uncalled**, for Batch 5 to pick up once a decision is made (1-line comment pointing at the BACKLOG entry). The Ready filter UI (`list.php`/`list.js`) was pulled back out for the same reason.
- New `tests/employee_recheck_filters_test.php` (23 assertions).

**Item 5 — Annual Summary through the shared DataTable helper + cycle filter + avatar column + Tab 4 Status filter (`4218f8c`)**

Confirmed the 4 pre-existing DOM-sourced callers (`payroll/detail.js`) are unaffected — they fall through to the original tbody-count branch unchanged.

One shared `AnnualIncomeSummaryModel::runFilterClause()` applied to every run-side query (`summary()`, `cellDetail()`, `rawDeductionRows()`, `buildMonthMeta()`) instead of copying the condition 5 times.
- Employee column across all 4 tables now shows avatar+name via the existing app-wide `apvPersonLineHtml()`/`apvAvatarHtml()` — no second avatar function. `AnnualIncomeSummaryModel` now selects+forwards `employees.profile_photo_path` (never selected before).
- Tab 4 (Monthly PIT) gained the Status filter it was genuinely missing (a first-pass claim that Branch was also missing was corrected during implementation — Branch was already present and wired).
- `tests/annual_income_summary_test.php`: +21 assertions (78 total).

- Tab 1 gained 3 checkboxes (ทั้งหมด/รายได้/รายหัก) — "All" is always derived as `income && deduction` (no state of its own), so checking All checks both, unchecking either unchecks All, and unchecking both auto-recovers to all-checked. ## Bugs found along the way

- **Lang files had 10 duplicate keys + 1 stray root-level key** (item 1) — `json_decode()` silently kept only the last occurrence, masking the duplication; a hand-rolled parser was needed to surface it at all.
- **`confirm_revert_message` was reused in the wrong grammatical form at both its real call sites** (item 1) — split into a correctly-named key rather than left ambiguous.
- **statutoryRateModal's Item Details form permanently vanished after the first open** (item 2a) — a Bootstrap Tab trigger-button `active` class was never cleared, silently no-opping every subsequent `.show()` call.
- **Add Rate Version's stacked modal visibly collapsed the outer modal's right column** (item 2c follow-up) — the relocated form left its anchor at 0 height; fixed with a measured min-height + placeholder.
- **`EmployeeModel::save()` had no company-level or employee-level gate on SSO/PVD dependent fields at all** (item 3) — any value could be saved regardless of either the "Enrolled" toggle or whether the company had the statutory item turned on.
- **`employees.is_payroll_ready` silently drifts from live readiness for every employee touched by either Origami sync path** (item 4) — neither sync write path ever recomputes it; a fix was built, tested, and found to be unsafe to turn on without a business decision + backfill plan (see BACKLOG).
- **`initSharedDataTable()`'s row-count-based `searching` default was always wrong for `data:`-driven tables** (item 5) — always read 0 from an empty-at-construction-time tbody; fixed to read the actual data array length.
- **The existing `.ais-cell-clickable` handler never forwarded `cycle_id`** (item 6) — a gap left over from item 5's own cycle-filter work, found and fixed one item later.
