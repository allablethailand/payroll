4. `database/migrations/2026-09-11_1_eed_installment_principal_interest_breakdown.sql`
   Adds `principal_amount`/`interest_amount` to `employee_earning_deduction_installments` — the per-installment breakdown behind item 4's 4-column table.

All 4 are additive (new columns/tables only), nullable where relevant, no backfill on any of them — every one has a verified working `-- DOWN` section (each was actually applied and rolled back against the real dev DB before code was written against it, not just written and assumed correct).

**Deploy step:**

- If the target database has run `scripts/migrate.php` before:
  `php scripts/migrate.php status && php scripts/migrate.php up`
- **First deploy to a NEW environment** (including production, which has never run this tool) is 4 steps, not 2 — do not shorten it:
  1. `php scripts/migrate.php status`
  2. Manually check every file `status` lists under "Unknown" against **that environment's own real schema** — do not assume it matches dev just because dev was already reviewed (dev's own 38 legacy files were marked via `mark-all-unknown` on 2026-09-10 dev-only; that action does not carry over to any other database)
  3. `php scripts/migrate.php mark <file>` per file confirmed already applied (or apply it deliberately some other way, then `mark` it) — or, once that same manual review is genuinely done for THAT environment specifically, `php scripts/migrate.php mark-all-unknown --reason="..." --yes` to record the whole batch in one command instead of one-by-one
  4. `php scripts/migrate.php up` — only now; it refuses to run anything at all while any file remains unresolved in "Unknown"

Rollback, if ever needed, in reverse of apply order: `php scripts/migrate.php down 2026-09-11_1_eed_installment_principal_interest_breakdown.sql`, then `down 2026-09-10_4_schema_migrations_add_reason.sql`, then `down 2026-09-10_3_deduction_destination_company_bank_account.sql`. (File 1, `2026-09-10_0_create_schema_migrations.sql`, should generally NOT be rolled back on a database anyone else still needs `scripts/migrate.php` to work against — its own DOWN drops the tracking table itself.)

## What changed, by item

**Item 0 — Migration runner tool (`scripts/migrate.php`)**
- New commands: `status`, `up`, `down <file>`, `mark <file>`, `mark-all-unknown --reason="..." --yes`. Replaces the old ad-hoc `mysql < file.sql` practice project-wide, which had already broken production once (running a file's `-- DOWN` section immediately after its own `-- UP` in the same invocation).
- `status`/`up` auto-detect whether a historical migration file is already applied (via a `CREATE TABLE`/`ALTER TABLE ... ADD COLUMN` marker regex) — 99 of 138 real historical files were auto-confirmed this way against the real dev DB; 38 have no marker the detector can extract (pure `DROP`/seed-only files) and land in an "Unknown" bucket `up` refuses to silently skip past.
- `mark-all-unknown` (added same day, follow-up) bulk-records a reviewed batch of Unknown files in one command instead of one `mark` call per file — refuses without `--yes`, without a `--reason`, or while any genuinely *pending* (not unknown) file exists.
- CLAUDE.md's own Database section rewritten to mandate this tool exclusively and to require the 4-step first-deploy sequence in every release note going forward (this note follows that rule).

**Item 1 — Hide empty blocks in Payroll Detail modals (logic only)**
- Calculation Breakdown modal: a section with zero line items now hides its whole block (header + table + total row) instead of an empty table with a placeholder row. Earnings and the Net Pay footer are the deliberate exception (always shown, even at zero, so "this period has zero income" is visible rather than silently missing).
- Raw Sync Data modal: a card whose every field is 0/blank/null hides entirely.

**Item 2 — Payroll cycle: multi bank account + payment-type auto-resolve**
- Investigation found nearly all of the originally-scoped work (multi-account cycles, per-employee scoped bank selection, a resolution priority chain) already shipped in a prior session. Real remaining gaps, all closed this batch:
  - (a) Cycle's "Default Payment Method" dropdown gained an explicit "follow each employee's own setting" option (sentinel `'auto'`, persists as NULL — no schema change) as the default for new cycles and for any existing NULL-valued cycle.
  - (b) A new cycle auto-checks its first bank account as default; an existing cycle saved with zero accounts now shows a clear warning instead of small gray hint text.
  - (c) Employee Detail's "Paid From Company Account" field previews which real account it resolves to when left blank.
  - (d) **Real bug fixed**: `PaymentVoucherReport` was reading the payroll cycle's own denormalized `bank_account_id` directly for every employee, ignoring per-run overrides and per-employee defaults entirely — a stale resolution left behind when the rest of this area (`BankTransferFileReport`, `BankAccountPaymentSummaryReport`) had already moved onto `PayrollRunEmployeeBankAccountModel::resolveForRun()`'s own precedence chain. Fixed to call the same method; added cross-check tests proving both reports resolve to the same account for the same run/employee.

**Item 3 — Deduction destination: "company" gains a level-2 (which bank account)**
- The 5 existing destination types (net pay / employee / company / other person / write-off) were kept; investigation found level-2 already existed for `employee` (pick which employee) and `other_person` (pick a saved payee or enter a new one) — only `company` had none. Added `bank_account_id` across all 4 write paths (one-time deduction, recurring deduction, manual line, per-run override), mandatory going forward when `payee_type='company'` is submitted, nullable for legacy data.
- `PayrollRemittanceModel::generateForRun()` now groups `company` remittances **per bank account** instead of one blanket row per run; an unspecified/legacy line gets its own group and is surfaced as an explicit warning, never silently dropped.
- UI: a company-bank-account picker added to all 4 relevant modals/editors, reusing the existing bank-account-options endpoint (no new endpoint). A "needs review" warning badge (new pattern) flags any `company`-type row with no account specified.

**Item 4 — Per-installment principal/interest breakdown**
- Investigation found both interest formulas (flat/add-on and reducing-balance/amortized) and the fee mechanism already fully implemented and correct — including the rounding-remainder-into-last-installment convention and the fee-timing question the original task treated as open (already resolved in shipped code as "spread evenly," confirmed to stay as-is).
- The real gap: the reducing-balance calculation already computed a per-installment principal/interest split internally but discarded it before returning, and the schema had nowhere to persist it. Added `principal_amount`/`interest_amount` to `employee_earning_deduction_installments`; `PayrollRunModel::recalculate()` now reads these straight off the persisted row into each payroll run's `deduction_breakdown` line, never recomputed. Employee Detail's installment table widened from 2 to 4 columns (`#`/Principal/Interest-or-Fee/Total) plus a totals footer.
- Audited `employee_earning_deductions` for `interest_rate` values that looked like an annual rate typed directly into the per-installment field (≥3%): **zero such rows exist** in the dev DB (the feature has no real usage yet).

## Bugs found along the way

- **`PaymentVoucherReport` stale bank-account resolution** (item 2d, above) — a real, currently-shipped bug affecting any company with more than one bank account and either a per-run override or a per-employee default set: the annual payment voucher would have shown the wrong paying account. Fixed this batch.
- **PVD dead columns (`employees.pvd_employee_rate`/`pvd_employer_rate`) — this is a Batch 3A bug, not a Batch 3B one.** It surfaced in this batch's history only because `docs/releases/2026-09-10-batch3a.md` (documenting Batch 3A's own item 7a) was written retroactively as part of this batch's own commit `54a2151`. Summarized from that note for completeness: `employees.pvd_employee_rate`/`pvd_employer_rate` existed in the schema but were never wired to anything (silently unused); confirmed 0 employees in the dev DB had either value set, so the fix had zero effect on any real employee's actual TH_PVD amount. See that release note for the full detail — no code in Batch 3B touches this.
