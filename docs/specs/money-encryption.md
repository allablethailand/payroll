# Design: การเข้ารหัสตัวเงินในฐานข้อมูล (Money-at-rest Encryption)

สถานะ: **ร่างเพื่อยืนยัน**
วางที่: `docs/specs/money-encryption.md`
ที่มา: ข้อกำหนดจากลูกค้า — กันทั้งคนที่เข้าถึง DB/backup โดยตรง และผู้ใช้ระบบที่ไม่ควรเห็น; ขอบเขตรวมยอดรวมระดับบริษัทด้วย

---

## 1. ปัญหา 2 อย่างที่ต้องแก้คนละวิธี

| ภัย | แก้ด้วย | ไม่ใช่หน้าที่ของ |
|---|---|---|
| (ก) คนเข้าถึง DB / dump / backup โดยตรง | **เข้ารหัสระดับแอป** (field-level) ด้วย key ที่ไม่อยู่ใน DB | สิทธิ์ผู้ใช้ |
| (ข) ผู้ใช้ระบบที่ล็อกอินได้แต่ไม่ควรเห็นเงินเดือน | **สิทธิ์ + masking** ระดับ role (`salary.view`, `salary.view_all`) | การเข้ารหัส — เพราะแอปถอดรหัสให้ทุกคนที่ผ่านแอปอยู่ดี |

ข้อนี้ต้องพูดกับลูกค้าให้ชัด: การเข้ารหัสไม่ได้ทำให้แอดมินระบบเห็นน้อยลง สิ่งที่ทำให้เห็นน้อยลงคือสิทธิ์

---

## 2. สิ่งที่ต้องยอมรับก่อนตัดสินใจ (ราคาของ field-level encryption)

1. **SQL คำนวณตัวเลขไม่ได้** — `SUM / AVG / ORDER BY / WHERE amount > x` บนคอลัมน์ที่เข้ารหัสทำไม่ได้ ทุกการรวม/เรียง/กรองตามยอดต้องทำใน PHP หลังถอดรหัส
   - ตาราง server-side DataTable ที่ sort/filter ตามยอด → ต้องเปลี่ยนเป็น client-side (annual-summary เป็น client-side อยู่แล้ว)
   - รายงานที่ใช้ `SUM()` ใน SQL → เปลี่ยนเป็นวน PHP หรืออ่านจาก **ยอดรวมที่เข้ารหัสเก็บไว้แล้ว** (§4)
2. **ต้องพึ่ง key** — key หาย = ข้อมูลเงินทั้งหมดหาย ไม่มีทางกู้ ต้องมี backup key แยกจาก backup DB และมีคนรับผิดชอบ
3. **ทุก path ที่เขียนเงินต้องผ่าน helper เดียว** — รวม Origami sync ที่ตอนนี้เขียน raw SQL (BACKLOG จาก Batch 4) ถ้ามี path ไหนหลุด จะได้ค่าปนกัน (plaintext/cipher) และรายงานผิดเงียบๆ
4. **ประสิทธิภาพ** — ถอดรหัสต่อค่า ~ไมโครวินาที; รายงานปี × 500 คน × 12 เดือน × 30 รายการ ≈ 180k ค่า ยังรับได้ แต่ต้องวัดจริงตอนนำร่อง
5. **Migration ครั้งเดียวย้อนกลับยาก** — ต้องมีช่วง dual-read และ backup ก่อน

ถ้าลูกค้าต้องการแค่ "ข้อมูลใน DB/backup อ่านไม่ได้" การเปิด **encryption at rest ของ MySQL/MariaDB (TDE) + เข้ารหัส backup** จะได้ผลข้อ (ก) ในราคาที่ถูกกว่ามาก โดยไม่เสียข้อ 1–4 — **ควรเสนอลูกค้าเป็นทางเลือกก่อน** ถ้าลูกค้ายืนยันว่าต้องเป็น field-level (เช่น DBA ของลูกค้าเองไม่ควรอ่านได้) ค่อยทำ §3

## 3. สถาปัตยกรรม (ถ้าทำ field-level)

**Helper เดียว**: `app/services/MoneyCipher.php`
- `encrypt(string|float|null $amount): ?string` — เข้ารหัส **สตริงทศนิยม** ("12345.67") ไม่ใช่ float; คืน base64(`v1:` + IV + ciphertext + tag)
- `decrypt(?string $cipher): ?string` — คืนสตริงทศนิยม; รับ plaintext ตัวเลขได้ในช่วง dual-read (ตรวจ prefix `v1:`)
- อัลกอริทึม AES-256-GCM, IV สุ่มต่อค่า (ค่าเท่ากัน cipher ไม่เท่ากัน — ค้นหาด้วยความเท่ากันไม่ได้ ซึ่งไม่จำเป็นสำหรับเงิน)
- **key**: อ่านจาก env/ไฟล์นอก webroot (`/etc/origami/money.key` หรือ env `MONEY_KEY`) ไม่อยู่ใน repo ไม่อยู่ใน DB; รองรับ **หลาย version** (`v1:`, `v2:`) เพื่อ rotate ได้โดยถอดของเก่าอ่านได้ต่อ
- ต้องเทียบกับวิธีที่ใช้กับฐานเงินเดือนอยู่แล้ว: ถ้าเข้ากันได้ให้ย้ายฐานเงินเดือนมาใช้ helper นี้ด้วย (นิยามเดียว) ถ้าไม่ได้ต้อง migrate ฐานเงินเดือนไปรูปแบบใหม่พร้อมกัน

**การเก็บ**
- คอลัมน์เงินเปลี่ยนเป็น `VARBINARY(255)` / `VARCHAR(255)` ชื่อเดิม (ไม่ต่อ `_enc`) เพื่อไม่ต้องแก้ทุก query แต่ **ต้องผ่าน model** — model ที่ read/write คอลัมน์เหล่านี้ห่วง encrypt/decrypt ใน 2 จุดกลาง: `hydrate()` (หลัง fetch) และ `beforeSave()` (ก่อน insert/update) — ห้ามมี `encrypt(` กระจายใน controller/view
- รายการคอลัมน์ที่เข้ารหัส = **config เดียว** `app/config/money_columns.php` (`table => [columns]`) ใช้ทั้ง model, migration, lint

**ยอดรวม (ตามข้อกำหนดว่ารวมด้วย)**
- ยอดรวมระดับ run/บริษัท (รวมจ่าย, รวมภาษี, รวม สปส. นำส่ง) **คำนวณใน PHP ตอน recalculate แล้วเก็บเป็นค่าที่เข้ารหัส** ใน `payroll_runs` (หรือตารางสรุป) — รายงานอ่านค่าที่เก็บ ไม่ต้องรวมใหม่ทุกครั้ง
- ยอดรวมต้อง recompute ทุกครั้งที่รายละเอียดเปลี่ยน (ผ่าน recalculate เดิม) — ไม่มี path อื่นเขียน

**สิทธิ์ (ข)**
- permission ใหม่: `salary.view` (ดูของตัวเอง/ทีมตาม scope), `salary.view_all`, `salary.export`
- helper แสดงผล `maskMoney()` → "••••" เมื่อไม่มีสิทธิ์ — ใช้ใน `fmtMoney()` เดิม (จุดเดียว) จึงได้ทุกหน้าอัตโนมัติ
- export/PDF/สลิป ตรวจสิทธิ์ก่อน render

**Log/Audit**
- audit log / ประวัติแก้ไข (ที่จะทำใน Batch 5) ที่เก็บ "จากอะไรเป็นอะไร" ของฟิลด์เงิน → เก็บค่าที่เข้ารหัสเช่นกัน (ใช้ helper เดียวกัน)
- ห้าม log ค่าเงิน plaintext ใน error log / debug

**Sync จาก Origami**
- ทุกยอดที่รับมาผ่าน `MoneyCipher::encrypt()` ก่อนลง DB — ต้องรื้อ raw SQL ใน sync path ให้ผ่าน model (BACKLOG เดิม) **ก่อน** เปิดใช้เข้ารหัส

## 4. แผนย้าย (ทำเป็นลำดับ ห้ามข้าม)

| ขั้น | ทำ | เกณฑ์ผ่าน |
|---|---|---|
| 0 | Inventory: Claude Code รายงานทุกคอลัมน์เงินทุกตาราง + ทุก query ที่ SUM/ORDER/WHERE บนคอลัมน์เหล่านั้น + ทุก path ที่เขียน (รวม sync) + วิธีเข้ารหัสฐานเงินเดือนปัจจุบัน | รายงาน ไม่แก้โค้ด |
| 1 | `MoneyCipher` + key loading + test (encrypt/decrypt/rotate/dual-read) + `money_columns.php` | test ผ่าน; ฐานเงินเดือนย้ายมาใช้ helper นี้ |
| 2 | รื้อ path ที่เขียนตรง (sync) ให้ผ่าน model | test sync เดิมผ่าน |
| 3 | ย้าย SQL aggregate → PHP หรือยอดรวมเก็บไว้ (§3) ทีละรายงาน โดย**ยังไม่เข้ารหัสข้อมูล** (helper ทำงานแบบ pass-through) | รายงานให้ตัวเลขเท่าเดิม 100% (golden test เทียบก่อน/หลัง) |
| 4 | Migration เข้ารหัสข้อมูลเดิมบน dev → เทียบ golden test อีกครั้ง | ตรงทุกตัวเลข |
| 5 | Prod: backup DB + backup key แยกที่ → migrate → ตรวจ golden → เก็บ backup plaintext ไว้ตามนโยบายลูกค้า | |

Rollback: migration มี `-- DOWN` ถอดรหัสกลับได้ตราบที่ key ยังอยู่

## 5. คำถามที่ต้องตอบก่อนเริ่มขั้น 1

1. ลูกค้ายืนยันว่าต้องเป็น **field-level** (ไม่รับ TDE + encrypted backup) ใช่ไหม — ถ้ายังไม่ได้ถาม ควรถามพร้อมอธิบาย §2
2. **key เก็บที่ไหน ใครถือ** — บน server เดียวกับแอป (กัน backup/dump หลุด แต่คนที่เข้า server ได้ยังถอดได้) หรือลูกค้าถือเองผ่าน secret manager/KMS (ต้องมี infra เพิ่ม)
3. ต้องมี **key rotation** ตามรอบไหม (ปี/ครั้ง) — กระทบว่าต้องมี job re-encrypt
4. รายงาน/หน้าจอไหนที่**ต้อง**กรอง/เรียงตามยอดใน DB จริงๆ (เช่น "หาพนักงานเงินเดือน > 50,000") — ถ้าไม่มี ข้อ §2.1 ไม่เจ็บ
5. เลขบัญชีธนาคาร (ไม่ใช่เงิน แต่ลูกค้ามักนับรวม) เข้าขอบเขตด้วยไหม
